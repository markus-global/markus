# Markus 架构脆弱性根因分析

> 2026-09-11 · 起因：「同一个 session 后续请求看不到历史」修复后，老板提出更根本的问题——
> 为什么这个系统总有脆弱的 bug？是不是架构问题？为什么总在打补丁、总依赖人工测试反馈？

---

## 0. 一句话结论

**不是「某个 bug 没修好」，而是三类硬约束缺位：状态归属契约、失败可见性、不变量测试。**

每一次修复本身都是对的；但修复所依赖的**隐式前提**既没有写在文档里，也没有被测试守住。
于是下一轮结构性改动（例如「把状态下放到 per-worker 工作区」这种正确方向的改动）会在
**没有任何人察觉**的情况下破坏这些前提。今天这个 bug 就是三个「单看都合理」的决定叠加出的
**必然窗口**，而不是偶发故障。

另外一个残酷的事实：本次修复前后，核心包 **2568 个测试全绿**——测试数量并不等于
不变量覆盖。真正的缺口不是「测试太少」，而是**测错了东西**：大量用例在断言实现快照，
极少用例在断言系统必须永远成立的性质。

## 2. 五类结构性根因

### R1 隐式共享可变状态 + 作用域静默变更 ← **今天的主凶**
`currentSessionId`、`activeScenario`、`turnModelOverride` 等状态从「agent 级单例」被下放成
「per-worker 工作区」（`workspace() = ALS ?? rootWorkspace`）。这是正确方向，但它**改变了
所有既有读取点的含义**：HTTP 线程读到的永远是 root 工作区，worker 读到的永远是自己的。
任何「由外部线程写、由 worker 读」的模式都会静默失效——今天正是如此。

**特征**：改动本身合法、代码能编译、既有测试全绿，但是语义已变。

### R2 静默降级：失败被伪装成正常
- `getRecentMessages(未知 id)` → `[]`
- `persistUserMessage` 失败 → 返回 `null`（客户端继续用占位 id）
- `getSession(查不到)` → 直接 `createSession` 新建
- `catch {}` / 仅 `debug` 级别地吞掉异常
- fire-and-forget 刷新无去重、结果可能乱序覆盖

**危害**：错误不再产生噪声，只在用户侧表现为「怪怪的」。**这是 bug 潜伏期长的首要原因**。

### R3 双存储 / 双 id 空间靠约定维持
`chatSessionRepo(cs_*)` 与 `MemoryStore(sess_*)` 是两套事实源，靠「绑定表 + 元数据」保持一致，
但没有单一 SSOT、没有启动自检、没有一致性告警。一旦绑定漏写（并发下常见），
系统就会「回退到瘦重建」（历史只剩 user/assistant 行，工具调用与结果全丢，实测 57 → 3 条）。

### R4 同一语义多实现
- stream 与非 stream 两条消息处理链路（今天发现：**只有非流式认显式 session id**）
- Legacy 与 hook 两套前端实现长期并存
- 两个并发闸各自独立
- 两套 id 命名空间各自解析

**后果**：改一条路径，另一条变成暗坑；「修好了」只在某条路径上成立。

### R5 缺不变量测试与提交门禁，验证依赖人肉
- 关键不变量（同会话历史连续、跨 worker 会话一致、重启可恢复、id 空间不混用）**零覆盖**
- 调试打印、死代码、空 `catch`、重复修复都能进仓
- 结构性改动没有「写者-读者」清单，全凭记忆

**结果**：老板成了唯一的集成测试环境。

## 3. 为什么「重构」反而放大脆弱性（机理）

这不是重构方向错了，而是**重构的验证方式错了**：

1. **结构性改动会合法地改变隐含前提。** 把状态从 agent 级下放到 per-worker 工作区，
   是一次架构升级；但它同时把「读 `currentSessionId` 就能拿到本次请求的会话」这个
   遍布全仓的**隐含假设**变成了假的。
2. **没有「写者-读者矩阵」。** 于是所有未被审计的读取点都变成定时炸弹——它们不像语法错误
   那样编译报错，而是**静默返回默认值**（空会话），最终表现为「agent 失忆」。
3. **默认并发开启放大了命中概率。** 单 worker 时「共享指针」和「请求会话」恰好等价，
   所以问题被掩盖；一旦默认 3 个 worker，任何共享指针都可能属于别的会话。
4. **结论**：重构的风险不在于它做了什么，而在于**它没有同步更新的那份依赖清单**。
   清单不存在 → 只能靠用户在生产里踩出来。

> 判断一个重构是否安全，不看「测试是否全绿」，而看「能不能说清哪些地方的语义被改变了」。

## 4. 对策（按杠杆排序，全部可执行）

### C1 写下并强制「状态归属契约」（1 天，立刻）
- 新增本文档配套的**写者-读者矩阵**：每一行 = 一个状态 × 谁写 × 谁读 × 哪个线程/工作区 ×
  是否允许隐式读。
- 代码级强制：per-worker 状态禁止跨线程隐式读。把「由 HTTP 线程决定 turn 会话」的入口
  从签名上删掉——**显式传值，不靠共享指针**。
- 本次已落地的样板：`sendMessageStream` 显式携带请求 session id；
  `handleMessageStream` 按「DB id 绑定的内存会话 > 工作区指针 > 新建」解析，
  且「有 DB id 但无绑定」必须告警。

### C2 消灭静默降级（本周，最高性价比）
规则：任何「查不到就返回空 / 就新建 / 就吞异常」都必须区分三态 ——
`found | missing | notLoaded`，后两者必须 `log.warn` + 打点。
- 本次已落地：`getRecentMessages` 对未驻留会话**先按 id 从磁盘懒加载**，未知/空 id 告警；
  会话历史加载失败不再被伪装成「新会话」（`null`=显式新对话，`undefined`=身份未知→保持原会话）。
- 待办：lint 门禁禁 `catch {}`、禁 `console.*`（一律走 logger，带上下文）。

### C3 单一事实源 / 消除 split-brain（本周）
- 对外唯一身份 = DB 会话（`cs_*`）；内存会话（`sess_*`）是内部缓存，
  绑定**只允许一处写入**（本次已改为在「实际处理该消息的工作区」写绑定）。
- 启动时/每轮做一次便宜的一致性自检：绑定双向一致、无孤儿内存会话、磁盘会话数对账。

### C4 多路径合流（2 周）
- stream 与 non-stream 收敛到同一个 `resolveTurnSession()` + 同一个消息处理内核。
- 删除并存的 legacy/hook 双实现（本次已清 1232 行死代码）。

### C5 「会话不变量」测试套件（**最高杠杆**，本次已启动）
本次新增 `packages/core/test/conversation-session-invariants.test.ts`（6 条不变量），
并用**变异验证**证明有效：把修复回退 → 6/6 全红。守住的性质：
1. 同会话第二条消息（即使被另一个 worker 处理）必须看到第一条的历史；
2. DB id 绝不被当作内存会话 key（无 split-brain）；
3. 未驻留会话必须能从磁盘懒加载（重启/被逐出后历史不丢）；
4. 未知/空 id 必须告警，不得静默返回空历史；
5. 并发下会话之间不串线；
6. 绑定缺失时行为必须可观测（告警），不得伪装成「空对话」。

**扩展方向**：任何会话/并发相关改动都必须先补一条不变量，再改代码。

### C6 真实链路冒烟门禁（本周）
起真 server + 真 SSE + 同会话两连发（3 worker），10 秒内跑完，进 CI 必过。
理由：单元测试再全，也覆盖不了「HTTP 线程写、worker 读」这类跨线程语义。

### C7 结构性改动强制附「写者-读者矩阵」+ 灰度
改状态作用域 = 必须先产出矩阵并逐格对账；禁止「顺手改作用域」。
这类改动的 review 重点不是代码风格，而是**矩阵是否有空格**。

### C8 交付卫生（本周）
- CI 必过：lint（no-console / no-empty-catch / no-unused）+ `pnpm quality` + 死代码检测。
- 合并前查重复修复：同一问题出现多个等价提交（今天发现 `2bbdc7d7` 与 `4454b4f3` 重复交付）。
- 测试环境隔离：本次发现本机存在 `OPENAI_API_KEY` 时测试会真实打 embedding 接口、
  单轮挂 ~10s——CI 噪声会掩盖真实失败，必须显式隔离。
