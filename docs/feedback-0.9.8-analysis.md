## 一、结论速览

用户整体评价 **非常正面**（多次肯定系统、表示要写好评录视频、愿意走通黑灯工厂），
但有一个被反复提及的**核心痛点**和几条**稳定性/可观测性缺陷**：

1. ⚠️ **Token 消耗过大是第一天就暴露的最大问题**——用户反复强调「刷太快」「一天近
   十亿」「纯聊天几千万」，并据此质疑上下文/缓存是否生效。
2. ⚠️ **API/模型供应商异常 → 任务卡死、页面刷不出、进程退出**——这是「服务会死」的
   直接观感，用户多次遇到「跑一天下不去、卡住、无进展」。
3. ⚠️ **可观测性不足**——AI 一直「思考中」，但看不到它到底卡在哪、作业在哪个 session、
   有没有在跑（用户对比 Codex 的可见性）。
4. ⚠️ **任务调度与依赖治理**——阻塞、双向依赖、两个任务同给一个 agent、异常后不重试、
   服务大盘自己挂……
5. ℹ️ **若干已在本分支解决/规划中**——per-agent 指定模型、token 成本归因、上下文工程
   缓存友好、session 工具可见性等，分支已落地部分内容。

下列章节：先给底层的「问题清单」，再逐条给出「对照 v0.9.8 之后的发展」——哪些已经解决，
哪些仍要深入排查，哪些需要单独设计。最后是分层的需求与任务（含依赖关系）。

## 五、优先级分层 & 建议路线图

### P0（先做——生存与信任）
- **S. 稳定性与容错**：API 异常不拖垮全局；进程崩溃可观测、可自动拉起；前端不死循环。
- **O. 可观测性**：把「思考中」变成「在干 XX / 卡在依赖 XX / 排在第 N」；能定位卡住点、看 session、看运行轨迹。

### P1（紧接着——成本竞争力）
- **G. Token 成本**：把 context-os（压缩/缓存/拆分）成果**并入正式分支**，给出 per-agent 成本归因，消除「建团队 700 万」式浪掷。

### P2（并行——成熟度）
- **F. 依赖与并发治理**：DAG 死锁检测、单 agent 并发默认策略、异常重试可配置、「拆多 agent」落地。
- **M. 模型管理**：per-agent 指定模型（分支已做）/按难度自动选模型/路由 fallback 验证。

### P3（规划——差异化）
- **I. 上下文/项目隔离**、**K. 知识库方案**、**U. UI 体验收口**（macOS 输入回车、付费技能 UI、内置终端提示）、**X. 文档与引导**。
