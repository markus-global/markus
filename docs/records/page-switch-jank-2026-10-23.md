# 桌面版切页卡顿：根因、实测与修复（2026-10-23）

## 1. 现象

Electron 桌面版在左侧栏切换页面（概览 / 团队 / 任务 / 产出 / 资产）时明显卡顿、掉帧，
而同一套 web UI 在右侧栏（独立 WebContentsView）或新开的浏览器标签里很快。

## 2. 根因

**所有访问过的页面都会永久保持挂载**（这是有意的：聊天流、滚动位置、表单状态在切页时不丢），
而"隐藏"用的是 `visibility: hidden` + `position: absolute`：

```ts
const HIDDEN_STYLE = { visibility: 'hidden', position: 'absolute', inset: 0, pointerEvents: 'none', zIndex: -1 };
```

`visibility: hidden` 只是不画，**子树仍然参与样式计算和布局**。于是：

- 整篇文档的 style recalculation / layout 范围 = 所有已访问页面节点之和；
- 每帧（这台机器 ProMotion 120Hz）都要走一遍，主线程常驻被占用；
- 每切一次页，React 提交 + 新页面激活时的重排要在这个巨大的文档上做一次 → 长任务、掉帧。

**成本随"访问过多少页面"单调增长**——所以是"用越久越卡"。

这也解释了桌面版与网页版的差异：桌面窗口是**长生命周期文档**，一天下来 7 个页面全挂着；
右侧栏视图 / 新标签是**全新文档**，只有 1 个页面。右侧栏还跑在自己的渲染进程里，
不跟主窗口抢同一个主线程。

## 3. 实测（真实应用 + CDP，非推理）

环境：`Markus.app`（Electron 35，Chromium 渲染进程，ProMotion 120Hz），
探针：`requestAnimationFrame` 间隔 + `PerformanceObserver('longtask')`，每次切换测 700ms。

| 场景 | DOM 节点 | 切页长任务 | 切页阻塞时长 | 最差帧 |
|---|---|---|---|---|
| 全新文档，仅挂 2 页（概览 / 团队） | ~1.8k | **0** | **0 ms** | 15 ms |
| 已访问 7 页（`visibility: hidden`） | ~15.4k | 3–4 个 | **183–430 ms** | 66–84 ms |
| 同一 7 页，把隐藏改成 `display: none` | ~14.6k | **0** | **0 ms** | 15–18 ms |

第三行是**同一次会话、同一个文档、同一份 DOM**，只把隐藏槽的 CSS 从 `visibility` 换成
`display` 后重测的结果——排除了"新页面自身渲染成本"和"数据请求"这两个干扰变量。
空转（idle）帧间隔也从 10.8ms（p95 32.8ms，2.5s 内 10 个长任务）回到 8.3ms / 0 长任务。

单页重量（隐藏时仍在被排版的量）：

| 页面 | 节点数 |
|---|---|
| 创建（AgentBuilder） | 8 145 |
| 产出（Deliverables） | 2 480–4 431 |
| 任务（Work） | ~2 900 |
| 聊天（Team） | ~1 270 |
| 社区 | ~913 |

"创建"一页就占全文档一半以上节点，它是当前最大的单点成本来源。

## 4. 修复

`packages/web-ui/src/App.tsx`：

1. `HIDDEN_STYLE` 由 `visibility: hidden; position: absolute; inset: 0; z-index: -1`
   改为 `display: none`。
   - React 状态不丢：组件仍然挂载，聊天流、滚动位置、表单内容都保留；
   - 子树退出 layout / paint / style，并同时退出无障碍树（`visibility: hidden` 不会）。
2. 每个页面槽加 `data-page-active="true|false"`，并在**真正由隐藏变为可见**时向槽
   派发一次 `markus:page-shown` 事件（首次挂载不派发，避免多一次无谓测量）。
   原因：`display: none` 下页面自测尺寸是 0×0，所有"挂载时量一次"的逻辑（图表、
   虚拟列表、编辑器）需要在回到可见时重新量。绝大多数基于 `ResizeObserver` 的
   实现会自动收到 0 → 真实尺寸的变化；事件是给有需要的地方留的明确接口。

单测：`vitest run --config vitest.web-ui.coverage.config.ts` → 79 文件 / 1095 用例通过；
`tsc --noEmit` 通过。

## 5. 残余风险（必须验证的部分）

- **首次挂载即测量的组件**：以前隐藏时也有真实尺寸，现在会读到 0×0。本机在 dev 环境
  逐页验证了 7 个页面：活动页里 canvas / 图表容器 / 虚拟列表均无 0×0 异常
  （任务页有 19 个 0×0 SVG，定位在页面内部自身折叠的面板里，与本改动无关）。
- **需要在真实打包版复测**：本次数据来自线上运行的打包版（CSS 就地替换 A/B）+ dev 服务
  （新代码正确性）。要交付给用户体验，需重新构建桌面包。
- 有页面可能在"不可见"状态仍依赖 `visibility` 继承（已全仓库 grep：无此用法）。

## 6. 下一步（按性价比排序，尚未实施）

1. **给挂载集合设上限**：现在 7 页全挂、两万节点。改为 LRU（例如保留最近 3 页）、
   其余真正卸载，可同时降低内存与"创建"页 8k 节点的常驻成本。代价：切回时重挂载 +
   重新拉数据，需要先量"重挂载成本"是否小于常驻成本。
2. **不可见页面暂停轮询/定时器**：`setInterval` 有 30 处，隐藏页仍在请求数据、跑状态机；
   它们同样产生主线程任务，与渲染成本是两笔账。
3. **首次挂载成本**（现在不再互相拖累，但单页首访仍慢）："创建"页 8145 节点值得单独做
   一次虚拟化/分页。
4. **回归护栏**：把本次探针脚本固化进 `scripts/`（切页长任务 / 最差帧 / 节点数），
   并给"隐藏槽必须是 `display: none`"加一条断言，防止被判据漂移悄悄改回去。

## 7. 结论一句话（第一轮）

不是 Electron 慢，是**"隐藏"用错了一个 CSS 属性**：`visibility: hidden` 的页面仍然全额
参与样式计算和布局，而桌面窗口把所有访问过的页面永久挂着，成本按节点总数累加；换成
`display: none` 后，同一份 DOM 下切页从"3–4 个长任务 / 约 200ms 阻塞"降到"0"。

# 第二轮：老板重编后"效果不明显"——真实数据复测（2026-10-23 15:20 起）

## 8. 第一步不是猜，是确认改动到底在不在跑

- 运行中的进程：`packages/desktop/dist-electron/mac-arm64/Markus.app`（15:16 启动），
  asar 15:09 构建。
- 桌面的渲染页**不是**从 asar 直接加载，而是 `win.loadURL(backendUrl)` → 由同进程内的
  后端在 `127.0.0.1:8056` 提供 web-ui 静态产物。
- 因此判据是**服务端实际发出的 JS**，不是 asar 里有字符串：
  `curl /assets/index-BDdyrMwv.js` → 含 `markus:page-shown`、`data-page-active`、
  `display:"none"`，**不含**旧写法。⇒ 改动确实在跑。

## 9. 复现台：第二个 Electron 实例（不动老板在用的那个）

```bash
# 复制最小身份子集（Cookies / Local Storage / IndexedDB / Preferences），
# 用独立 user-data-dir + CDP 端口起第二个实例；它会健康检查到 8056 已有同版本服务
# → 直接复用，不再起后端、不碰数据库，也不受单实例锁影响。
Markus --user-data-dir=/tmp/markus-perf-<hhmm> --remote-debugging-port=9223
```
这样拿到的是**同一份生产产物 + 同一套真实数据 + 已登录会话**的可测窗口。

## 10. 复测结果：修的是真问题，但只解决了一半

同一会话、同一份 DOM，A/B 只换隐藏槽的 CSS（真实数据）：

| 隐藏槽写法 | 平均切页 | 长任务总量 | 慢帧（>34ms） |
|---|---|---|---|
| `display:none`（新） | 125ms | 690ms | 8 |
| `visibility:hidden`（旧） | 159ms | 1455ms | 20 |

⇒ 新写法把长任务砍掉约一半，**但没有归零**。逐页看（7 页全挂，文档 ~14k 节点）：

| 目标页 | 切页耗时 | 长任务 | 该页节点数 |
|---|---|---|---|
| 团队 | 123–130ms | 100–114ms | 1,477 |
| 资产 | 115–139ms | 50–57ms | 8,168 |
| 任务 | 45–54ms | 0 | 2,908 |
| 产出 | 35–68ms → **337ms** | 0 → **6 个 / 650ms** | 1.1k → **28,892** |
| 设置 | 51ms | 0 | 105 |
| 概览 | 38–40ms | 0 | 413 |

**新发现（第一轮没量到的）**：单页节点数会无限长。产出页（交付物树）在展开若干分组后
达到 **28,892 节点 / 滚动高度是视口的 33.8 倍**，命中一次就要在**一帧里**做完
28.7k 节点的 style+layout+paint → 337ms 一次，且与"隐藏槽用什么 CSS"无关。
这就是老板体感"还是卡"的主因：不是隐藏页的成本，是**被点亮那页自己的体量**。

## 11. 第二轮修复：跳过视口外内容（已实施）

在 `packages/web-ui/src/index.css` 增加三个工具类（真实数据 CDP 就地注入验证）：

| 场景 | 基线 | 加 `content-visibility:auto` 后 |
|---|---|---|
| 产出页（28,892 节点） | 337/334/344ms，6 长任务（~650ms） | **141/186/182ms，1–3 长任务（55–218ms）** |
| 资产卡片（8,168 节点） | ~125ms，50–57ms 长任务 | ~115ms，**0 长任务** |

落地位置：
- `.cv-row` → `pages/Deliverables.tsx` 的分组容器与每一行条目；
- `.cv-stack > *` → `components/Masonry.tsx` 的每一列子元素（资产/探索/技能/模板共用）。

验证：`npm run typecheck` 通过；`vitest run --project web-ui` → 79 文件 / 1095 用例通过。

## 12. 还没解决的（下一轮的目标）

- **团队页每次切过去 ~120ms、其中约 100ms 是 JS**（CPU profile：React 调度 24ms、
  `@tanstack/react-virtual` 的 `measureElement` 8ms、i18next `formatLanguageCode` 6ms，
  其余散落在渲染里）——它不是 DOM 重，是**每次点亮都重算一遍**。
  （顺带排除一个猜测：不是 Intl 格式化器重复构造，计数为 0。）

- **产出页可以长到 28.9k 节点**这件事本身：`content-visibility` 只是让"不看的不要算"，
  真正该做的是展开分组按需渲染（当前折叠容器里 303 个子元素照样被创建）。
- **回归护栏**：把 CDP 探针固化进 `scripts/`，并给"隐藏槽必须是 `display:none`"加断言。
