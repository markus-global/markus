# 多 Agent A2A 场景的缓存命中率问题：第一性原理分析

**日期**：2026-10-29　**分支**：`analysis/a2a-cache-hit-rate`
**数据来源**：`~/.markus/llm-logs/2026-10-29.jsonl`（741 次真实调用的完整载荷）+ `~/.markus/data.db` 的 `audit_logs`（provider 回报的 token 用量）
**观测窗口**：北京时间 10:48–11:15，GEO 团队密集 A2A 期间

---

## 一、先纠正一个口径问题：暴跌了多少？

同一份数据，两个分母得出两个结论：

| 口径 | 分母 | 命中率 |
|---|---|---|
| 错 | `inputTokens + cacheRead`（DeepSeek 的 `prompt_tokens` **已含** cached，再加一次就是重复计数） | **48%** |
| 对 | `inputTokens`（prompt_tokens 本身） | **94–96%** |

后面所有数字都用对的这个。**但 94% 仍然是假的安心感**——按分钟看真实曲线：

| 北京时间 | 调用 | prompt tokens | 命中率 |
|---|---|---|---|
| 10:51 | 26 | 2.3M | **63.8%** |
| 10:53 | 36 | 6.2M | **82.1%** |
| 11:05 | 45 | 15.6M | **83.4%** |
| 11:06 | 43 | 14.0M | 90.7% |
| 其余分钟 | ~590 | ~180M | 94–99% |

窗口总计：**740 次调用 / 218M prompt tokens / 0.7M output tokens**。平均每次调用带 29 万 prompt tokens。

所以真实的问题是两层：
1. **整体重放量离谱**（218M : 0.7M）——命中率再高 3 个点也救不回来；
2. **有几分钟结构性塌陷**——那是可定位、可修的 bug 面。

---

## 二、第一性原理：prompt cache 到底是什么

抛开所有提示词工程技巧，缓存命中的充要条件是四件事同时成立：

1. 同一模型 + 同一账号；
2. **从第 0 个 token 起，前缀逐字节相同**（不是"语义相同"，是字节相同）；
3. 前缀长度超过 provider 的最小阈值；
4. 距离上一次相同前缀的调用，在 TTL 之内。

于是：

```
命中率 = P(本次前缀与某条已有缓存条目逐字节相同)
      = f(不同前缀的数量, 每个前缀的复现密度, TTL)
```

**推论（这是全部优化空间的边界）**：
- 想提高命中率，只有三条路：**减少不同前缀的数量**、**提高单个前缀的出现频率**、**让可变的东西不出现在前缀里**。
- 任何"把状态塞进 system 或 history 头部"的设计，本质是在**制造新前缀**，命中率必然掉。
- 前缀的**共享长度**由第一个差异字节决定。今天这个差异字节出现在第 **21,248** 个字符处。

## 三、实测到的五个根因（按代价排序）

### R1. 一个频道 = N 份独立副本（结构性，最大一块）

A2A 群聊没有"唯一一份转录"。每个参与者各自持有一份 session：

```
channel_dm:a2a:<channelId>:<peer>_<selfAgentId>
```

实测同一个频道 `agt_cd114c0a | a2a`，4 个参与者 4 份副本：

| agent | 消息数 | 字符数 | 单次 prompt tokens |
|---|---|---|---|
| cd114c0a | 874 | 886,683 | 686,534 |
| ff94d383 | 557 | 772,553 | 600,435 |
| cea7bc1a | 397 | 760,536 | 448,935 |
| dee76d7a | 386 | 488,257 | 354,371 |

**同一段对话被当作 4 条不同的 prompt 前缀计费。**

跨 agent 的字节共享只有 **21,248 字符**（就是平台 L0 那段公共规则），占 system 的 60–67%；从第 21K 字符起（agent 自己的 ROLE），每个 agent 立刻分叉——**对话正文（几十万字符）在分叉点之后，因此共享率为 0**。

这就是为什么"多 agent 场景命中率低"：**缓存的单位是前缀，而 A2A 把同一份内容复制成 N 个不同的前缀。** 单 agent 时这问题不存在，所以单 agent 场景的数字一直很好看。

### R2. 团队文档（agent 可写的文件）躺在 system 缓存段里

**初版结论（错的）**：`isConverse` 截断导致 system 长度来回跳变。

**核验后的真相**：同会话内 system 长度**完全没变**（33362 → 33362）。精确 diff 显示变化点全在 `## GEO 优化团队 — 工作规范（Norms）` 那一段——是**另一个 agent 在 11:05 用 `file_write` 改了 `NORMS.md`**，而团队规范被拼在 system 的缓存段里，于是**全团队所有在跑的会话前缀同时作废**（窗口内 9/25 个会话出现 system 字节变化，公共前缀从 33k 塌到 28k）。

`isConverse` 只造成**跨会话**的 35836 vs 41867 差异（同一 agent 并发跑 human chat / a2a 等不同 scenario，`## Current Interaction Mode` 那段不同），不影响同会话缓存。

**判据**：任何 agent 能写的文件，都不得进入缓存前缀。`knowledge.md` 早前就是按这条规则移出去的，团队文档漏了。

### R3. state checkpoint 不会被原地改写，但会永久累积

**初版结论（错的）**：checkpoint 在 index 2 被反复重写，每次损失 66.8%。

**核验后的真相**：hash 追踪显示 checkpoint 在固定 index 上 **0 次内容变化**——它是会话第 2 次调用时一次性插入，之后就不动了。那个 66.8% 是拿 3 条消息的极小 prompt 当分母算的，绝对浪费只有 ~1.4 万 token/会话。

**真正的问题是累积**：每次状态变化就 append 一个新的 checkpoint，永不回收。

| 指标 | 实测（10-29 窗口） |
|---|---|
| checkpoint 总数 | **247 个** |
| 累计字符 | **3,401,033** |
| 单会话最多 | 26 个 / 474,695 字符（其中最新一个只有 ~19k） |

也就是说那个会话 **96% 的状态载荷是已被后续覆盖的旧副本**，每次调用全量重放。

**注意**：不能"只留最新一个"。checkpoint 只写**变更段**，所以最新那个天然缺少早先写过的段（实测 `## Team Status`、`## Notebook` 只存在于旧 checkpoint 里）。正确解法是**按章节合并、每章取最新正文**——合法，因为写者的不变量就是"每段正文是该段的完整当前正文"，最新者权威。

### R4. 用户消息被就地改写并永久增长（真 bug，最严重）

实测（`cs_315368b6c6c54bb3`，同一 index=55）：

```
556 → 587 → 618 → 649 → 680 → ... → 1145 字符
每次 LLM 调用 +31 字符，连续 37 次，永不停止
```

根因在 `context-engine.ts#sanitizeMessageSequence`：

```ts
prev.content = prev.content + '\n\n' + msg.content;
```

`prev` 是 `session.messages` 里的**真实对象引用**。合并结果被写回了存储，但被合并的那条没有从存储里移除（`result.push` 只影响本次返回值）。于是**每次调用都对同一对消息再合并一次**——存储被永久污染。

它长在历史中间，后面 45 条消息每次全废（~1.46M 字符）。**更糟的是内容失真**：模型读到的是同一句话重复 37 遍，而不是用户说的那一次。

### R5. A2A 历史无界增长，且工具结果原文全留

单会话剖面（874 条消息 / 886,683 字符）：

| 角色 | 条数 | 字符 | 占比 |
|---|---|---|---|
| user | 49 | 383,823 | 52% |
| tool | 276 | 310,365 | 35% |
| assistant | 281 | 11,129 | **1.3%** |
| system | 1 | 33,362 | 4.5% |

真正"模型说的话"只占 1.3%，其余 87% 是重放的输入和工具原文。即使命中率 96%，剩下 4% × 68 万 = **每次仍有 2.7 万未命中的 token 付费**。

## 四、优化方案

分三层。**A 是结构性改造（收益最大），B 是机械性 bug（立刻可做），C 是度量。**

### A. 结构性改造：反转前缀布局（**待评审，未实施**）

这是唯一能把 A2A 重放量真正降下来的改动，也是唯一动语义的改动，所以单独说清楚。

**今天的前缀布局：**

```
[平台 L0 ~21K][agent ROLE ~12K][对话正文 0.7M][本轮增量]
                 ↑ 分叉点在这里，后面 0.7M 全部无法跨 agent 共享
```

跨 agent 字节共享只有 21,248 字符（60–67% 的 system），从 agent 自己的 ROLE 起就分叉；而**对话正文在分叉点之后**，因此共享率为 0。N 个参与者 = N 条独立缓存条目 = N 倍重放。

**目标布局：**

```
[平台 L0 ~21K][频道公开转录 0.7M][agent ROLE ~12K][私有工具结果][本轮增量]
                                  ↑ 分叉点挪到最后
```

N 个参与者共享同一段前缀，**N 条缓存条目塌缩成 1 条**。

**必须同时满足的四个约束（缺一不可）：**

1. **转录必须逐字节一致**。不是"语义一致"——同一句话在 A 的 prompt 里和在 B 的 prompt 里字节相同。这要求转录用一个确定性序列化器产出，并作为**唯一写者**（不能各 agent 自己拼）。
2. **私有工具结果必须在分叉点之后**。每个 agent 的工具输出天然私有，只能放尾部。
3. **ROLE 后移不能削弱指令遵循**。这是主要风险：ROLE 目前在 system 头部。可行折中——provider 层面 `system` 字段独立于 `messages`，可以保持 `system = 平台L0 + ROLE`（不变），只把**频道转录**从 messages 里提到一个共享前缀位置。这样既不动 ROLE 位置，也让转录可共享。
4. **不能靠压缩历史换指标**。转录是共享事实，压缩它就等于所有 agent 同时失忆。

**实施顺序（建议）：**

| 步骤 | 内容 | 可独立验证的判据 |
|---|---|---|
| A1 | 抽出频道转录的确定性序列化器（唯一写者） | 同一频道两个 agent 的转录字节完全相同 |
| A2 | 把转录放到分叉点之前 | 同频道两 agent 的 prompt 公共前缀 > 90% |
| A3 | 私有工具结果/ROLE 移到分叉点之后 | 缓存条目数从 N 降到 1（按 provider 统计） |

**预期收益**：A2A 场景重放量最多降 4 倍（实测同频道有 4 个参与者副本，68.6万/60.0万/44.9万/35.4万 token）。
**风险**：指令遵循质量。必须做 A/B，且回滚成本低（它是布局改动，不改数据）。

### B. 机械修复（**已实施**，本次提交）

| 编号 | 问题 | 修法 | 落点 |
|---|---|---|---|
| B1 | 团队文档（agent 可写）在 system 缓存段里，任一成员编辑即全团队前缀作废 | 团队公告/规范移入**变化门控的 volatile 尾部**（与 knowledge.md 同一判据）；`## Team Data Directory` 留在稳定段（路径不变且 agent 需要知道去哪读） | `context-engine.ts#buildSystemPrompt` |
| B2 | state checkpoint 永久累积（247 个 / 340 万字符，单会话最多 26 个 / 47 万字符） | **按章节合并、每章取最新正文**（无损：写者不变量是"每段正文=该段完整当前正文"）；合并结果落在**最后一个 checkpoint 的位置**；不修改存储对象；确定性输出 | `context-engine.ts#collapseStateCheckpoints`（新增） |
| B3 | `sanitizeMessageSequence` 直接改写存储消息对象 → 同一句话每次调用 +31 字符，37 次 | 合并写入**新对象**（`result[last] = {...prev, content: ...}`），不再原地改 | `context-engine.ts#sanitizeMessageSequence` |

**为什么 B2 不能用"只留最新一个"**：checkpoint 只写**变更段**，最新那个天然缺少早先写过的段（实测 `## Team Status`、`## Notebook` 只存在于旧 checkpoint）。按章合并才是无损的。

### C. 度量修正（**已实施**，本次提交）

| 编号 | 问题 | 修法 |
|---|---|---|
| C1 | `/api/usage` 用**算术平均**：`Σ(各agent命中率) / 全部agent数`。闲置 agent 给 0% 投满票，一个大 agent 等于一个小 agent | 改为 **token 加权** `Σ(cacheReadReported) / Σ(cacheDenominatorTotal)`，只统计有采样的 agent；`aggregateCacheHitRate()` 放进 `provider-helpers.ts`（已是"唯一定义点"），不再造第四种口径 |
| C2 | "无测量"被渲染成 0% | 聚合函数返回 `null` ⇒ 响应带 `cacheHitRateUnknown: true`，前端必须显示"未知" |
| C3 | 缺"重放比"指标 | 新增 `computeReplayRatio(prompt, output)`，`/api/usage` 返回 `replayRatio`（本次实测 218M : 0.7M ≈ 311:1） |

### 实测暴露的残余问题（**不是我引入的，是原来就有**）

同一 session `cs_51d3f2b304a74142` 内，system 在两种 mode 之间交替：

```
05:37:07 human_chat sysLen=38817
05:38:01 a2a        sysLen=36230   ← 前缀 0% 复用
05:38:07 human_chat sysLen=38817   ← 前缀 0% 复用
05:38:11 a2a        sysLen=36230
...  同一会话内 human_chat:8 次 / a2a:5 次
```

分叉点固定在 `## Current Interaction Mode`（公共前缀 34,550 / 38,817）。原因：**A2A 回复被就地处理在发起它的那个会话里**，于是人机会话与 A2A 会话共用一条历史，而两者的 system 段不同 → **每交替一次就作废整条前缀**。

这是 R2 的真实形态（我最初报告的"isConverse 截断"是错的，但"同一 agent 多套 system 互相踩"这个方向是对的）。修法：**把 `## Current Interaction Mode` 移出 system 到尾部**（已实施，见第七节）。

> **更正（Owner 2026-10-29 指出）**：本文档初版把"让 A2A 回合开独立会话"列为
> 可选的修法之一，这是**错的**。
>
> `agent.ts:2437` 的会话选择顺序本就支持两者：
> ```ts
> sessionId: awaitOriginSessionId              // reply_in_session → 回发起会话
>   ?? channelSessionId                        // 默认 → 独立频道会话
>   ?? `a2a_${this.id}_${a2aConversationId}`   // 无 channel → 独立 a2a 会话
> ```
> **默认模式本来就是独立会话**——这个能力早已存在，不是待补的功能。
> 而 `reply_in_session` 按设计就应把对方回复并进发起会话（代码注释：
> "route the reply into the ORIGIN session so the delegating thread continues
> where it left off"）。这是**特性**，不是缺陷；把它当 bug 去"修"，等于删功能。
>
> 结论因此更强：既然 mode 混合是**设计意图**，`system` 就**绝不能**随 mode 变。
> 移入尾部是唯一正确的修法，而不是"绕过问题的折中"。

- 三项机械修复与度量口径**已验证生效**，可合入。
- 剩下两个结构问题（N 份副本、mode 交替作废前缀）都需要设计决策，不宜在验收阶段夹带。

## 七、A 方案上线验证（2026-10-29 14:25 重启后）

把 `## Current Interaction Mode` 移入 volatile 尾部 + **永不门控**后，用同一会话
（human 与 a2a 共用 `cs_51d3f2b304a74142`）实测：

| 指标 | 修复前 (13:35–14:00) | 修复后 (14:25+) |
|---|---|---|
| system 长度 | **38,817 ⇄ 36,230 交替** | **恒定 34,508** |
| system 版本数 | 2 | **1**（跨 8 次 human + 2 次 A2A 回合） |
| system 是否含 mode 段 | 是 | **否** |
| human↔a2a 切换点的前缀复用 | **0%**（div@0，占该小时 58.2% 的 token） | **94.6% / 91.7%** |
| 全程平均前缀复用 | — | **94.6%** |

**关键印证**：那次 A2A 回合与 human 回合共用同一个 sessionId、同一份 34,508 字符
的 system —— 切换点不再塌陷。修复前同样的切换每次都整条前缀作废。

**"永不门控"豁免的两处现场证据**：
1. 实时上下文里 `## Current Interaction Mode` 出现在 `[SYSTEM] [Live context]`
   尾部并**全量渲染**；
2. 同一块的 `[Background state — unchanged this turn: …]` 摘要列表里**不含**
   该节（其余 9 个状态段正常门控）—— 说明它每轮都在发，没有被摘要掉。

**设计要点（否则会退化）**：volatile 尾部是变化门控的，直接放行为指令会在 tool
loop 里被摘要掉。因此必须同时 (a) 列入 `ALWAYS_FRESH_VOLATILE_SECTIONS`，
(b) 排除出 durable checkpoint（每轮都发已保证送达，再存一份只是把 2.6k 字符
复制进被重放的历史）。

**契约变更迁移**：旧断言 9 处（4 文件）从「system 文本」改为「模型实际看到的
完整 prompt」；其中 2 处原断言「mode 段在 system 里」，改为断言「在 volatile 里」。
回归：core 262 文件 / 3422 测试全绿。

**第三轮复测（`reply_in_session: true`，17 次调用 / 5 个 A2A + 12 个 human 回合）**：

| 指标 | 结果 |
|---|---|
| system 版本数 | **1**（34508 字符，human 与 A2A 完全相同）|
| A2A 回合前缀复用 | 94.6% / 91.7% / 93.6% / 99.5% / 99.5% |
| human 回合前缀复用 | 81.8% ~ 98.8% |
| 总体平均 / 最低 | **95.7% / 81.8%**（最低值是重启后首次调用 = 冷启动）|

对照修复前：同样的 human↔a2a 切换每次 **0%**，占该小时 58.2% 的 token。

**双向验证（Secretary 侧实证）**：同为这一轮往来，Secretary 收到的消息用的是
普通 `agent_send_message`（未设 reply_in_session）→ 它落在独立的
`channel:dm:a2a:...` 会话，其上下文里**只有 A2A 内容、没有人机对话内容**。
说明两条路径各自按设计工作：

| 路径 | 会话落点 | 是否混合 |
|---|---|---|
| 默认（无 reply_in_session） | 独立 `channel_dm:a2a:*` | 不混合 |
| `reply_in_session: true` | 回发起会话（orchestrator 侧） | **按设计混合** |

## 七、不建议做的事

- **不要调 cache_control 断点数量**。断点只决定"从哪里开始存"，不决定"前缀是否相同"。今天的问题在前缀内容，不在断点位置。
- **不要盲目压缩历史长度**。压到 10 万 token 会让命中率高 2 个点，但 A2A 的对话完整性直接受损——这是拿正确性换指标。
- **不要在 provider 层做"多账号轮换"来摊费率**。缓存按账号隔离，轮换 = 每次都冷启动，净亏。
