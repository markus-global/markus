## 二、四类噪音，四类根因（这才是要修的）

### 1. 把「我一条命令能做完的事」建成卡
- `环境前置 · 建 worktree`：分支 worktree 早就在 `…/agents/agt_*/workspace/markus-card3` @ `9390b6b2`，我建卡时没查。
- `卡7 · 更正需求正文行号`：改几个 `:23 → :99` 的引用，一次文本编辑，被我做成卡。
- **判据**：如果「做」比「写卡面」快，那就不该有卡。

### 2. 把「返修」做成新卡，而不是打回原卡
- 卡1/卡2 标了 completed，但交付物不在被检分支树里 → 我建了 `卡1R`、`卡2R`。
- 结果是同一份事实两条轨迹 ⇒ **第二写者**，正是我在核查报告里批的病。
- **正确做法**：打回原卡（review → in_progress），让交付物与卡是 1:1。新建承运卡只在原卡确已终结时用。

### 3. 把「范围外的新发现」塞进同一需求
- `安全 · POST /api/resources/bindings 可自证升档 autonomy`（真问题，但属权限族，不属主干接线）
- `下一轮 · 异常阻塞判定第二写者 + Thread 视图数据源`（未复现的投机发现）
- **结果**：需求变成杂物筐，Reviewer 无法判断「这张卡算不算这个需求的完成度」。

### 4. 用「轮询卡」代替「等一句 + 自己查一次」
- `探针 · 每小时检查 /api/health`：一张 scheduled 卡，maxRuns=48，只为发现「Owner 是否已重建实例」。
- 真实成本：每小时一个执行轮次；收益：一次 `curl`。且平台已有 blocked 状态与唤醒机制。
- **判据**：能用一次手动检查替代的，不要建定时任务。

## 五、以后怎么防（写进准则的 3 条）

1. **建卡前先问三句**：这事我能不能一条命令做完？原卡是否还活着（能打回就别新建）？它属不属于本需求的范围？
2. **一卡一交付物**：卡片数量上限 = 真实剩余工作项数量；「元工作 / 环境准备 / 改文档引用」一律不单独开卡。
3. **不打回就新建 = 制造第二写者**：交付物不在树、验收不通过 → 打回原卡，不新建 R 卡（本轮的卡1R/卡2R 是历史遗留，不再重犯）。
