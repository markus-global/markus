## 1. 中心命题：super-organization

> **super-organization = super agent × super 协作机制**

这是全文的验收判据。写成乘积而不是加法，不是修辞——它直接决定工程优先级。

**推论 1（因子为 0 时，另一因子白做）**
单 agent 弱（不会自己接管责任域、不会自己判断事件该不该变成工作）时，协作机制投入再多，也只是把弱 agent 组织得更好。**N × 0 还是 0。** 所以「用组织形态弥补单 agent 弱」在工程上是**无效**的，而不只是不优雅。

**推论 2（协作机制也可能是 <1 的因子）**
设计得不好的协作机制，会让 10 个 agent 小于 1 个 agent：审批排队、上下文割裂、消息扇出、每次交接重新解释背景。
→ **判据：加了协作机制之后，单个 agent 完成一件事的端到端延迟不得上升。** 上升了，它就是个 <1 的因子，应该删而不是优化。

**推论 3（「super」只有一个度量）**
**单位人类注意力产出**：加人、加机制，只有当它让人**更少**介入每单位工作时才算 super。产出升了、但人的待办同步升了——那不是 super-organization，只是更大的 organization。

### 1.1 两层的最小能力集

| 层 | 最小能力集 | 反例（看似有、实则无） |
|---|---|---|
| **super agent** | ① 能接管一个责任域并**自己**配置（仓库 / 社交账号 / IM 频道 / 数据集 / 知识库 / 工单队列）② 能判断事件该不该变成工作（gate）③ 能判断它属于哪条流（thread）④ 能有条件等待而非轮询 ⑤ 无人指派时能自己发现该做的事 | 只有心跳的 agent；只在被 @ 时才醒的 agent；把「我负责这个小红书账号」写在 ROLE.md 里的 agent（那是人写的散文，不是平台事实） |
| **super 协作机制** | ① 权限与审批单一事实源 ② 上下文按流归并、不串味 ③ 任务/交付/审查可追溯 ④ **协作不增加单兵延迟（因子 ≥ 1）** | 靠群发同步的组织；靠人肉转述的交接；开 6 个面板才知道现在该干什么的看板 |

### 1.2 两个必须先纠正的旧判断

**旧判断 A：「super-agent 与 Markus 不是同一种物种，Q1（该不该做）在 Markus 里几乎不存在。」**
错。这句话听起来像洞察，实际是免责声明——等于承认「Markus 单 agent 天生弱，所以用组织形态补」。真实情况：agent 一旦被指派「负责某个仓库/账号」，Q1 每天都要回答；我们现在既没有「谁负责」这个事实，也没有让 agent 自己接管一块地的工具，于是 Q1 被转移成了「人在聊天里喊它」。**掩盖不等于不存在。**

**旧判断 B：「照抄 super-agent 的 Router 会解一道 Markus 没有的题。」**
错。Router / Thread / Source 是 L0（单 agent 自主性）的基础设施，**必须抄**。Markus 的差异只在 L1（协作治理）——而且 L1 应该是**叠加**，不是**补偿**。判据：把某个 agent 单独拎出来，它还能不能自己把一件事做完？答不能，就说明这个设计在拿组织形态掩盖 L0 的弱。

## 2. 第一性原理：一个 agent 平台到底在调度什么

任何一个 agent 平台，无论叫什么架构，都在回答四个问题，且只有这四个：

| # | 问题 | 回答错了的后果 | 单 agent 产品（super-agent） | 多 agent 组织平台（Markus） |
|---|---|---|---|---|
| Q1 | **一个外部事件，该不该变成工作？** | 变成噪音（该忽略的做了）或漏做（该做的没做） | 核心难题（Eval / gate / admission table 全在做这件事） | **同样存在，只是被现在的设计掩盖了**：agent 一旦负责某块地，它每天要回答的就是这一问（见 §1.2-A） |
| Q2 | **这份工作属于哪条上下文？** | 上下文割裂（结果对不上）或串味（张冠李戴） | 核心难题（Thread + Subscription） | **核心难题**，但现在是隐式的 |
| Q3 | **谁有权做、做到哪一步？** | 越权、不可追责 | 弱（Policy 只管「谁能发起」，不管交付审批） | **强项**：requirement→task→review→approve 已经在跑 |
| Q4 | **人的注意力该被花在哪里？** | 平台变成噪音源，人开始忽略平台 | 核心原则（整个 000-philosophy 只有这一句） | **弱项**：注意力被分散在 Work / Team / Notifications 三个面 |

### 2.1 一条推论：注意力预算必须按通道分别计量

super-agent 把「注意力」定义为**唯一**的稀缺资源，据此规定「每条消息、每个设置、每个面板元素都必须赚回它消耗的注意力，否则删除」。这是一条可执行约束，因为它给出了判据：**删除不赚回注意力的东西**。

Markus 目前的注意力成本（2026-10 实测教训）：
- A2A DM 自动回踢（`api-server.ts:2604-2652`，`DM_MAX_DEPTH=6`，cooldown 是 per-channel，10 个 channel = 10 倍吞吐）→ 一次「同步 9 个人」= 9 个全量回合；
- 任务评论**不唤醒任何人**（`mentions=[]` 时不唤醒）→ 写了 24,313 字，实际是「废气」；
- 心跳是定时器，哪怕无事也醒（虽有指纹跳过，见 `heartbeat.ts:86`）。

共同点：**平台消耗注意力的通道是「消息数 × 接收者数」，而不是「信息量」**。super-agent 把成本锁定在「信息量」上——它没有群发，只有「一条流上的后续」。

**对 UI 的约束：任何新增通知面板，如果不能减少其他面板的通知量，就是在增加噪音。** 这也是实现篇「Inbox 必须替代而非新增」的来源。

## 3. Super-agent 的机制（逐层拆解，附证据）

### 3.1 对象模型：七个概念，一个方向

`docs/001-domain.md` 给出的流程是单向的：

```
Source ──Trigger──▶ Thread ──batch──▶ Eval(gate+assessment) ──Decision──▶ Ticket + Mandate
                        │                                                      │
                        └──Subscription fan-out──────────────────────────────▶ │
                                                                               ▼
                                                                          Assignment ──▶ Executor(Session + 目录)
```

| 概念 | 关键规则（原文要点） | 解决什么 |
|---|---|---|
| **Source** | 持有读取位点；定义什么算事件；**在进入领域之前**丢弃机器人自己的消息和不在监听范围的事件；把 Trigger 翻译成所属 Threads 与回复地址 | 重启不重放 |
| **Trigger** | 不可变事件；属于一个或多个 Thread；**同一 Trigger 被接受两次只产生一个 Ticket** | 幂等与审计的原子单位 |
| **Thread** | 按时间排序的 Trigger 流；**同一时刻最多一个 Eval 在跑**；持有自己的 Subscriptions、运行中的 Eval、决策历史 | 给 Eval 一致的视图与上下文 |
| **Eval** | 两层：gate（确定性）+ assessment（模型研判）；**不持有状态** | 决定新工作是否开始、继续或停止 |
| **Decision** | `accept` / `stop` / `ignore` / `unavailable` | 唯一判据载体 |
| **Ticket** | **只有 Eval 能创建**；引用 Mandate；open→ended，人发消息可恢复（除非人喊停）；**自己定义状态，不跟随 Executor** | 授权工作的单位 |
| **Mandate** | 不可变；记录 Policy 版本、范围、强度、命中的规则、发送者身份；只有「人喊停」或「重新校验失败」能撤销 | **为什么可以干这件事，能干到哪一步** |
| **Assignment** | Ticket 与一个 Executor 实例的绑定；pending→running→ended，**独立于 Ticket** | 执行器在领域外，但「谁在执行」在领域内 |
| **Subscription** | Ticket ↔ Thread 多对多；订阅 Thread 上任何后续消息**扇出给所有活着的 Ticket，不检查发送者**；人发的消息走这条路时**不经过 Eval** | 后续讨论无需再次 @ 到 agent |

**最值得抄的不是任何一个概念，而是 `docs/001-domain.md` 末尾的「rejected concepts」表**——他们明确列出了**被拒绝的设计**及理由：

- ✗ 「等待中 / 已撤销」的 Eval 状态 —— *等待属于 Source，Eval 从不等待*；
- ✗ Eval 自己调度延迟的 Trigger —— 否则 Eval 反向依赖 Source；
- ✗ 一个 Thread 最多一个活 Ticket —— 一条流可以承载多个独立工作；
- ✗ 「追加到 Ticket」这种 Decision —— 追加是订阅扇出，不需要 Eval；
- ✗ Ticket 状态跟随 session —— Ticket 可以被移交、恢复、多执行器跑；
- ✗ **从报告的自由文本推断「在等人」** —— 分类需要结构化事实，执行器必须用结构化字段提问；
- ✗ 策略变更时取消运行中的 Ticket —— 取消会留下半成品，改为记录+投递。

**为什么这张表值钱**：它不是设计，是**否证记录**。它把「为什么我们不这么做」写进了 SSOT，使下一个人不会把同一个被否掉的想法再提一遍。Markus 的 ADR 大量是「我们怎么做」，几乎没有「我们为什么不做 X」——这是可以立刻补的（成本极低，收益是防止架构漂移）。

### 3.2 两条通路：全文最重要的一张图

super-agent 的所有复杂度都来自承认：**「新工作」和「已有工作的后续」不是一件事**。

```
通路 A（冷启动，贵）：事件 → Gate → Assessment → Decision → 新 Ticket
通路 B（热续接，便宜）：事件 → 命中已订阅 Thread → 直接进该 Ticket 的 Worker，不经过 Gate、不产生 Decision
```

原文（`docs/002-authorization.md`）：
> 「Every message on a subscribed Thread reaches its subscribed Tickets as context, including messages from bots and CI. **This delivery bypasses the gate and grants no new authority.**」

这句话里有两层，缺一不可：① **绕过 gate**（省一次判定）——性能；② **不授予新权力**（Mandate 不变）——安全。只做第 1 层会得到「谁都能往正在跑的活儿里插话」的系统；只做第 2 层则没有收益。

数据支撑（原文 7.1 节）：去掉直通后任务完成时间基本不变，但 **Router 决定数 +30%，读缓存 token 23.23M → 31.77M（+37%）**。直通的收益不是「更快」，而是**省掉 37% 的上下文重读**——在 Markus 这种每回合都注入大段 system prompt 的平台上，这个比例只会更高。

### 3.3 批量与串行：批在 Thread 上，串在 Thread 内

- **批的边界是 Thread**：`Engine.evaluateDue()` ——「一个 Thread 一次 Eval，**其间到达的 Trigger 合并成下一批**」（`docs/007-architecture.md`）。
- **串行的边界也是 Thread**：`docs/001-domain.md` —— Thread「**At most one Eval runs on it at a time**」。
- **不同 Thread 的 Eval 并行**，互不阻塞。

所以它不是「把邮箱里所有东西攒一批丢给模型」，而是「**同一条流的多个事件合并成一次判断**」。差别：Markus 的批依据是「队列非空 + 阈值 + 同实体」，super-agent 的批依据是「同一条流」——前者会跨流合并，后者不会。

## 4. Markus 的现状（机制级，附文件证据）

### 4.1 入口与队列：一次入队，三层隐式调度

```
web-ui 发送 → api-server 路由 → Agent.sendMessage()
  → 构造 MailboxItem { sourceType, payload:{content}, metadata:{senderId,responsePromise,…}, extra:{sessionHint,channelKey,onEvent,cancelToken,scenario} }
  → mailbox.enqueue()                              // packages/core/src/mailbox.ts:591 入队去重
  → AttentionController 被 'mailbox:new-item' 事件唤醒（无轮询）  // attention.ts:185 "There is NO polling"
  → dequeue 头项 → 可能触发 pre-triage 清理 / 合并 / deliberation
  → delegate.processMailboxItem(item, batchItems?, batchContext?)   // attention.ts:81
  → Agent.processMailboxItemCore()                 // agent.ts:2272
  → switch (item.sourceType) { … }                 // agent.ts:2366
```

队列模型（`mailbox.ts`）：
- **优先级队列**：数字小者优先；**同优先级内 LIFO**；
- **租约**：`MAILBOX_LEASE_TTL_MS = 15min`（`mailbox.ts:45`），`ownerId = agentId#pid#seq`，跨进程唯一，只有认领者能续租/释放/完成；
- **状态**：`queued` / `processing` / `deferred` / `completed` / `merged` / `dropped` / `failed`；
- **幂等**：`resolveReinjectDecision()` 是「新增/抑制/复用原行回队」的**全库唯一**判定实现（`mailbox.ts:200-240`）；
- **实体亲和锁**：`entityLocks: Map<entityKey, holder>`（`mailbox.ts:305` 附近），「同一实体永不并发」。

这套队列写得相当扎实——租约、owner 校验、僵尸清理、幂等重投、单写者判定，都是踩过坑之后的产物。**问题不在实现质量，在于语义定位**：它是一个「每个 agent 一个」的**私人收件箱**，因此只能回答「我现在该处理哪一条」，无法回答「这条消息属于哪条流、那条流现在在等谁」。

### 4.2 隐式批处理：三层，各做一件不同的事

| 层 | 位置 | 依据 | 产出 | 问题 |
|---|---|---|---|---|
| L1 入队去重 | `mailbox.ts:591-600` | 同类型 + 同实体（comment 类） | 合并进既有 item | 只覆盖 comment，语料窄 |
| L2 预分拣合并 | `mailbox.ts:494 consolidateByEntity()` | `taskId` / `requirementId` / `channelKey` | 一个「综合上下文块」，把多条 payload 拼进 survivor 的 `content` | **直接改写 payload 正文**；需黑名单护航 |
| L3 deliberation | `attention.ts:712` → `agent.ts:4225 performDeliberation()` | LLM 全量判读队列 | 选一条执行、其余 complete/drop/defer | **每条队列消息都可能烧一次额外 LLM**；决策不可审计 |
| （旁路）batch 头 | `agent.ts:2282-2300` | 上层传入的 batchItems | `[BATCH PROCESSING — N items]` 头 + 逐条拼接 | 拼装发生在 prompt 里（in-band） |

**关键判断：这三层加起来 ≠ router，它 = 一个「队列整理器」。**
判据很简单：router 的输出是**关于工作流的决定**（接受/挂到哪/忽略/延后），这三层的输出是**关于顺序和呈现的决定**（先处理哪条、拼成什么样）。前者改变系统状态，后者只改变下一轮 LLM 看到的字节。

**合并改写正文的两个硬伤**（`consolidateGroup()`）：
```ts
survivor.payload.content += `\n\n---\n\n${typeLabel}${item.payload.content}`;
```
1. **平台替 Agent 改写了用户消息的内容**——与「平台只守硬不变量，其余交还给 Agent；越界时拒绝 + 给可行动提示，不要悄悄替 Agent 改写内容」直接冲突；
2. **结构从载荷推断**——多条消息的边界靠 `\n\n---\n\n` 这种 in-band 文本容器表达，任何一条原始消息里恰好含 `---` 就会被当成结构。

正确做法不是「加转义」，而是**不让合并产生新的正文**：合并产出**引用列表**（`items: [{id, kind, summary, ref}]`），由渲染层在固定段里展开，正文各自独立存放、各自可回溯。固定段还顺带解决 prompt 缓存友好性（合并数量变化不改变 prompt 形状）。

### 4.3 实体亲和锁：它有 Thread 的形状，没有 Thread 的语义

`packages/shared/src/types/mailbox.ts:82-95`：

```ts
export type MailboxEntityScope = 'task' | 'requirement' | 'user' | 'conversation' | 'channel' | 'system';
export const ENTITY_SCOPE_ORDER = ['task','requirement','user','conversation','channel','system'];
```

每个 item 类型在注册表里声明自己参与哪些作用域（`entityScopes`，`shared/types/mailbox.ts:112-130`），运行时取「第一个能解析出值的」作为锁键。

注释里有一段极其坦诚的历史记录：
> 「**会话优先**（conversation 而非 user）是刻意的：聊天的并发隔离维度是**会话/标签页**，不是发起人。同一个人在不同 session tab 里同时发言应当真并行……早期版本把 `user` 排在 `conversation` 之前，使同一个人的多标签页被全量串行（实测交接日志出现 **41 次 `user:*` 冲突**）。」

**这证明了两件事**：① Markus 已经在做「同一上下文的消息串行」——这正是 Thread 的核心语义；② 但它通过**锁**实现，锁的语义只有「互斥」，没有「顺序、订阅、归并、可见性」。所以收益只有「不打架」，代价（队头阻塞、作用域排错、41 次冲突）全都要付。

更严重的是 `attention.ts` 里 `sessionLockKey()` 的注释：
> 「实体键由 `resolveEntityKeys` 从 payload **声明**的信息推出。但一个回合真正改写的资源是『它将要跑进去的那个记忆会话』，这两者可以不重合……实测：worker 1 持有 `conv:cs_9809eb…` 跑聊天回合，worker 2 拿到 `system:agt_…` 就在**同一个记忆会话**里并发跑起了后台回调回合……用户看到的是一条 0 字回复。」
>
> 「所以锁的**键必须由『回合会跑进哪个会话』决定**，而不是由『消息自称属于谁』决定。」

这是**结构从载荷推断**的一次真实事故，而修复方式（额外补一个 `sessionLockKey()` 钩子）是**加守卫**，不是**改结构**——因为「这条消息属于哪条流」这个事实，在系统里**根本没有一个一等对象来承载**。它能被算出两种值，恰恰是因为它不是一个东西，而是一句推理。

### 4.4 会话模型：三个 id、四条绑定规则、零个「流」

| 概念 | id | 权威 | 谁在用 |
|---|---|---|---|
| DB 聊天会话 | `cs_…`（`chat_sessions`） | **权威**（UI 全以它为键） | web-ui、历史、消息落库 |
| 内存记忆会话 | `sess_…`（MemoryStore） | 上下文单位 | context-engine、压缩、回忆 |
| 任务会话 | `task_…` | 执行单位 | task_execution 回合 |
| A2A 频道 | `channelKey` | DM/群聊 | a2a bus |

`session-bindings.ts` 写得很清楚：这张表**只服务存量旧会话**（`cs_` → 旧 `sess_` 的别名），「它**不是**第二个权威：唯一的权威是 `cs_`」。这是正确的收敛。

但问题在上一层：**「我和这个 agent 关于这件事的对话」这件事，没有 id。** 用户看到的是「会话列表」，agent 看到的是「当前会话指针」，任务卡看到的是「task session」，三者之间只有**约定**（`resolveTurnSession()` 这一处解析），没有**对象**。super-agent 用 Thread 把这件事变成对象：有 id、有顺序、有订阅、有阶段、有历史决策。**Markus 缺的就是这个对象。**

### 4.5 生命周期与主动性

- `HeartbeatScheduler` 是**定时器**（`setInterval`），首次延迟加随机抖动防尖峰；
- `activeHours` 支持时区（`minutesOfDayInTimeZone`，纯函数）；
- `heartbeatStateFingerprint(queued, activeTaskIds)`：**只在「队列内容 + 活跃任务」变化时才跑 LLM 巡检**，指纹不变则只写时间戳。

指纹设计是对的（注释明确批评了旧实现「队列深度相同即 skip / 深度变化即巡检」的双向误判），但它治的是**症状**：本质仍是「定时醒来，看看有没有事」，只是加了一个便宜的「没事就跳过」判定。

对比 super-agent：**没有心跳**。事件自己会来（`prompts/orchestrator.md`：「never wait for them with sleep, polling or job waits」）。他们的「没事」状态就是**没有回合在跑**，而不是「跑了一个什么都不做的回合」。

**结论**：如果事件能自己唤醒会话，就不需要「定时醒来」这种降级方案。`rest` 工具的意义在于：让「等待」成为一次**可被中断的、有条件的**挂起，而不是一次**无条件的轮询**。

### 4.6 外部接入：有适配器，没有抽象

`packages/comms/src/platforms/registry.ts:102`：
```ts
export type InboundMode = 'webhook' | 'socket' | 'polling' | 'gateway';
```
每平台声明自己支持哪些模式，`resolveInboundMode()` 按「socket → polling → 显式关掉 webhook → 默认 → gateway → webhook」选。

**这是一个「传输层」抽象，不是「事件层」抽象。** 它回答「消息怎么进来」，不回答：
- 这个来源的**哪些**事件值得进入领域？（admission）
- 这个事件属于**哪条流**？（thread）
- 这条流**是否已经有主人**？（subscription / 直通）
- 这个事件**是否已被处理过**？（事件级幂等 —— 现在只有 mailbox 层的幂等键）

super-agent 的 `Source` 是**领域概念**：持有读取位点、定义什么算事件（含只在时间上成立的条件）、在进入领域前丢掉机器人自己的消息与监听范围外的事件、并把每个 Trigger 翻译成「属于哪些 Thread + 回复到哪个 Channel」。

另一个容易混淆的东西：`packages/core/src/external-gateway.ts` 名字像 webhook 网关，实际是**外部 agent 注册 + 签名令牌 + 消息投递**（`ExternalAgentRegistration` / `GatewayToken` / `GatewayMessage`），用于接入第三方 agent 运行时。**它与事件订阅无关**，不能当外部事件基础设施用（建议改名 `external-agent-registry`）。

### 4.7 UI：三个面，没有一个面回答「现在需要我做什么」

`packages/web-ui/src/pages/` 的主面（按体量）：`Work.tsx`（8,226 行）、`Team.tsx`（6,449）、`AgentProfile.tsx`（3,066）、`Settings.tsx`（4,003）、`Deliverables.tsx`（2,105）、`Home.tsx`（1,412）。

要回答「现在有什么需要我」，必须在 **Work（等审批的卡）× Team（等回复的 agent）× Notifications（铃铛）** 三处来回扫。三处各自都真实，但没有一个「按『在等我』排序的合并视图」。super-agent 的 Overview 页就是干这件事的，排序键是 **stage = 「在等谁」**——`person/*` 永远排在最前。

### 4.8 责任资源：平台只认「仓库」一种，而多数 agent 不写代码

| 能力 | 现状 | 代码证据 |
|---|---|---|
| 一个 project 挂多个仓库 | **已有** | `projects.repositories`（每项含 `localPath` + `role: primary\|secondary`），`sqlite-storage.ts:308` |
| 一个 project 挂多个团队 | **已有** | `projects.team_ids TEXT DEFAULT '[]'` |
| 治理策略 / 报告节奏 / 知识库路径 / onboarding 配置 | **已有** | `governance_policy` / `report_schedule` / `knowledge_base_paths` / `onboarding_config` |
| **agent 能自己建/改 project（含挂仓库）** | **已有** | `create_project` / `update_project` 支持 `repositories` / `teamIds` / `governancePolicy`（`core/src/tools/project-tools.ts:240,280`），`create_project` 自动记 `createdBy: ctx.agentId` |
| agent 被 onboard 到 project | **有服务，没工具** | `ProjectService.onboardAgent(agentId, projectId)`（`project-service.ts:140`） |
| **社交账号 / IM 频道 / 数据集 / 工单队列的责任归属** | **完全不存在** | `shared/src/types` 里没有任何账号/频道/队列实体（`llm.ts` 的 `accountId` 是模型厂商账号，不是业务账号）；comms 只有平台适配器，没有「哪个 agent 负责哪个账号」 |
| **agent「负责」某个资源** | **不存在** | `AgentConfig` 无任何归属字段；`tasks.project_id` 只表示「这张卡属于哪个项目」 |
| **agent 自绑 / 自解绑** | **不存在** | 工具面只有 `list_projects / get_project / create_project / update_project / delete_project / project_stats` |
| **绑定之后的后果** | **不存在** | 没有 Thread、没有 Source，事件无从归属 |

**最关键的一行是倒数第四行**：平台唯一能表达的「责任资源」是**仓库**，而这只是其中一种。一个内容 agent 的真实责任域是「这个小红书账号 + 这个 X 账号」，研究 agent 是「这个数据源 + 这组 RSS」，客服 agent 是「这个工单队列」——**它们现在一个都表达不了**。

**可验收的判据**：给一个内容 agent 一个陌生的小红书账号 + 一个竞品 RSS 源，它应当能在**一次对话内**自己完成——声明负责 → 配来源与规则 → 收到第一条真实信号并提出下一步，全程无人点 UI。

## 5. 概念对账

### 5.1 主对账表

| super-agent | Markus 现状对应物 | 关系判定 | 差距 |
|---|---|---|---|
| **Source** | `comms/platforms` 适配器 + `InboundMode` | **传输层 vs 领域层** | 无「什么算事件」「读到位点」「进领域前过滤」 |
| **Trigger** | `MailboxItem` | **同一个东西，但承载了太多轴** | 一个枚举混了来源/类别/优先级/UI/执行语义 |
| **Thread** | 实体亲和锁键（`task:`/`conv:`/`channel:`） | **形状相同，语义缺失** | 只有互斥，没有顺序/订阅/归并/阶段 |
| **Eval（gate + assessment）** | triage + deliberation + consolidate | **替代品，但不可审计** | 决策不落库、无 reason、无 matched rule |
| **Decision** | `DecisionType = pick\|continue\|preempt\|cancel\|defer\|merge\|delegate\|drop`（`shared/types/mailbox.ts:332`） | **词汇已具备，语义是「接下来处理哪条」** | 缺 `accept/attach/stop/ignore` 这层**关于工作流的**决定 |
| **Ticket** | `Task`（`tsk_`） | **形似神不同** | Task 是治理对象；缺「执行侧的工作单位」 |
| **Mandate** | requirement 审批 + task 审批 + reviewer≠assignee | **Markus 更强** | 双层授权 vs 单层 |
| **Assignment** | 会话绑定 + 并发 worker 槽位 | 部分对应 | 无「一个工作单位 ↔ 一个执行实例」的显式绑定与报告回传 |
| **Subscription** | **不存在** | **最大缺口** | 后续事件无法直通已订阅执行体 |
| **Stage** | 无（`TaskStatus` 是治理状态） | **缺失** | 无法回答「卡在谁那儿」 |
| **Policy / accept mode** | 无（有心跳，无「主动档位」） | **语义空白** | 无法表达「观察但不行动」 |
| **Panel（Overview）** | Work / Team / Notifications 三面 | **分散** | 无「在等我」的合并视图 |
| **Rejected concepts** | 无（只有 ADR 的 how） | **可低成本补齐** | 缺「为什么不做 X」的否证记录 |

### 5.2 三处「名字不同、其实是同一个东西」

**① mailbox 批量 ≈ router？—— 一半对。**
对的一半：都在回答「攒着的这些，先处理哪个 / 要不要一起处理」，都在降低单条消息的边际成本。
错的一半：router 的输出**改变工作流状态**（新建工作单位、挂到已有流、忽略并记录理由）；batch 的输出**只改变下一轮 LLM 看到什么**。把后者当前者用，会得到一个「很会整理，但从不做决定」的节点——这正是 `deliberation` 的处境：它会挑一条、把其余 complete/drop，但**它不会说「这条属于那张卡，我把它挂过去」**。
→ **要把批处理提到前台，但提到前台的不是「批处理」，是「决策」。** 批处理留在后台做性能；决策浮到前台做可解释。

**② 同 task / 同 session 线性处理 ≈ threads？—— 对，而且是同一个问题。**
Thread 干三件事：**(a) 串行保证；(b) 订阅直通；(c) 上下文归并**。实体锁只做了 (a)，而且做得很贵。(b)(c) 才是用户能感知的：
- 没有 (b)：同一张卡的后续评论、同一个 PR 的 CI 失败、同一人在同一会话的追问，都要重新走「入队 → 可能合并 → 可能 deliberation → 可能被插队」→ 用户感知是**「它怎么又忘了我刚才说的」**；
- 没有 (c)：上下文靠 `resolveTurnSession()` 每回合临时解析，解析错就串味（那次 0 字回复事故）。

**③ 「主动 agent loop」+ router session 不停止？—— 对，但要以「router 承担等待」为前提。**
worker 永不停止 = 每个执行体都烧钱（心跳风暴的结构性版本）。router 不停止 = **只有一个**节点保持在线，它负责「等待」，且等待**可被事件打断**。两者成本差一个数量级。

## 6. 结构诊断：七个根因（按可修性排序）

### R1 · 「消息类型」这一个枚举混了五条正交的轴
`MAILBOX_TYPE_REGISTRY`（`shared/types/mailbox.ts:112-130`）为每个类型声明：`label`（UI）、`defaultPriority`（调度）、`category`（UI 分组）、`icon`（UI）、`invokesLLM`（执行语义）、`entityScopes`（并发）。
**加一个新消息类型 = 同时决定 UI 文案、图标、分组、优先级、是否烧 LLM、参与哪些并发作用域。** 六件事彼此独立，却被绑在一个 key 上。后果：新类型必须六件事一起想，于是「先抄一个最像的」→ 抄错的代价是静默的（抄了 `heartbeat` 的 `entityScopes: ['system']`，该类型就永远与任何具体实体并发，全部串行）。
**修法**：拆成三条独立的轴（§7.2）。

### R2 · 「这条消息属于哪条流」没有一等对象，只能靠推理
证据是 `sessionLockKey()` 那段注释：实体键从 payload 推出，而回合真正跑进的会话是另一回事，两者可以不重合 → 同一记忆会话被两回合并发写 → 0 字回复。
**修法**：让「流」成为对象，锁的键 = 流的 id。**这是删机制**：`sessionLockKey()` 这个钩子本身可以消失，因为 item 上直接带着 `threadRef`。

### R3 · 合并改写正文，且用 in-band 分隔符表达结构
**修法**：合并产出 `items[]` 引用列表，正文各自不动；渲染层在**固定段**里展开（固定段顺带解决 prompt 缓存友好性）。

### R4 · 「串行」被当成安全机制，而不是连续性机制
实体锁语义是「互斥」，可观测后果是队头阻塞（41 次 `user:*` 冲突）、无法解释「为什么这条等很久」、且不保证顺序语义（LIFO）。
Thread 语义是「这条流上的事件按时间顺序，一次只有一个处理者」——同时给出顺序、互斥、以及「谁在处理」的可观测性。
**修法**：把串行从「锁」升级为「流 + 单写者」。锁保留为实现手段，不再是语义载体。

### R5 · 主动性只有一种形态：定时自检
`heartbeat` 是 mailbox 里的一种 item（`entityScopes: ['system']`，优先级 3），语义是「到点了，醒一下，看看有没有事」。三个结构性限制：无法表达「观察但不行动」（没有 `observe`）；无法表达「我对这个来源的这类事件感兴趣」（没有订阅）；无法表达「我在等一个条件」（`schedule_wakeup` 本质仍是轮询）。
**修法**：三件套 —— `Trigger`（事件能来找你）+ `Subscription`（订阅一条流的后续）+ `rest(wakeOn)`（等待有终止条件、可被打断）。心跳降级为兜底保活。

### R6 · UI 上「在等我」被拆成三处，且各自用自己的口径
Work 用 `TaskStatus`，Team 用「有没有未读」，Notifications 用「有没有事件」。三个口径互不承认 → 幽灵态（「进行中」UI 无法被权威状态否决）。
**修法**：一个派生 `Stage` + 一个合并 Inbox。判据：**任何一个「需要人」的对象，在 Inbox 里恰好出现一次，且消失的原因必须能在详情页查到。**

### R7 · 「我负责这块地」既不是字段，也不是工具
R1–R6 全部是「消息进来之后」的问题。在那之前还有一个更根本的缺口：**agent 不知道自己负责什么，平台也不知道哪块地归谁。**
三重缺失（证据见 §4.8）：没有归属事实（`AgentConfig` 没有任何资源字段）；没有自绑工具（只有「管项目」，没有「认领它」）；没有后果（即使记了归属，也没有 Thread/Source 让事件落到它头上）。
后果是一串连锁的「弱」：agent 只能等人派活 → 看起来像「被动」，实际是**没有入口让它主动**；外部事件没有收件人 → 只能由人转述或丢掉；「主动」只剩心跳一种形态（R5）。
**修法（三件一起，缺一不可）**：`ResourceBinding` 对象（§7.3）+ 自绑工具面（实现篇）+ `Source` 事件（实现篇）。缺第三件，前两件就是装饰。
**判据**：给 agent 一个它从没接过手的资源（社交账号 / 数据源 / 仓库），它能在一次对话内自己接住第一条真实信号。

## 7. 目标模型：三条正交轴 + 五个一等对象

### 7.1 设计约束（先定边界，再定形状）

1. **不新增一个「系统」**。所有新概念必须是现有东西的**命名化与归一化**，否则我们会同时维护两套。
2. **加实例 = 注册一个适配器**，不允许改调度核心。注意：**轴不等于枚举**（见 7.2 的修正）。
3. **Agent 的语义不能被平台改写**：平台只做归一化、排序、可观测，不改正文。
4. **人类消息永远优先**：任何新增节点都不得让人等它。
5. **缓存友好**：注入内容尾部可变、头部固定（不可因为「这批有几个事件」改变 prompt 的形状）。

### 7.2 三条轴（并修正一个概念错误）

现在的 `MailboxItemType`（15 个值）同时编码了「从哪来」「属于什么」「多急」「要不要跑 LLM」「和谁互斥」「长什么样」。拆成三条独立的轴：

```ts
// ── 轴 1：事件从哪来（决定归一化与幂等键）
// 这不是枚举，是注册表：加平台 = 注册一个适配器，不改核心类型
export interface SourceAdapter {
  prefix: string;                    // 'gh' | 'xhs' | 'rss' | 'im-feishu' …
  normalize(raw, headers): Trigger | Trigger[] | null;
  idempotencyKey(raw, headers): string | null;
  verify?(raw: Buffer, headers, secret: string): boolean;
}

// ── 轴 2：它属于哪条流（决定串行、订阅、上下文归属）
// 这不是枚举：流就是「它关于哪个实体」，实体 id 本身就是键
export type ThreadRef = string;      // 'tsk_7f3a' | 'req_2b1c' | 'xhs:brand_01'

// ── 轴 3：它在等谁（派生，不存储）—— 唯一合法的闭集
export type ThreadStage =
  | 'person:approval' | 'person:answer' | 'person:review' | 'person:blocked'
  | 'system:queued' | 'idle' | 'working';
```

**上一版我把「正交的轴」写成了「封闭的枚举」，这是概念错误。** 轴是独立变化的方向，它可以是枚举、注册表或命名空间字符串。把轴实现成枚举，就要求所有未来实例在编译期已知——这正是硬编码的来源。所以三条轴里**只有「在等谁」必须是闭集**（它是 UI 排序契约），另两条是注册表 + 命名空间。

**优先级从「类型的属性」变成「规则的函数」**：

```ts
function priorityOf(t: Trigger): MailboxPriority {
  if (t.kind === 'chat' && t.actor.kind === 'human') return 0;   // 人永远第一
  if (t.thread?.stage.startsWith('person:')) return 1;
  if (t.kind === 'a2a' && t.addressing === 'direct') return 1;
  if (t.kind === 'external') return 2;
  if (t.kind === 'schedule') return 4;
  return 3;
}
```

拆开后：**UI 关注 kind 与 stage（映射表独立），调度关注 priority（规则函数），并发关注 threadRef（对象）**。三者不再互相绑架。

### 7.3 五个一等对象

```ts
export interface Thread {
  id: string;                     // thr_*
  /** 这条流关于哪个实体：一套命名空间，不是分类法 */
  ref: ThreadRef;                 // 'tsk_...' | 'req_...' | 'cs_...' | 'xhs:brand_01'
  owner?: { agentId: string; sessionId: string; since: number };
  subscriptions: Array<{ ticketId: string; agentId: string; purpose: 'own' | 'context' }>;
  events: ThreadEventRef[];       // 追加型日志，只追加不改写
  createdAt: number;
  lastActivityAt: number;
  // stage 不存储，读取时由 deriveStage() 算
}

export interface Trigger {
  id: string;
  kind: 'chat' | 'im' | 'a2a' | 'task' | 'requirement' | 'external' | 'schedule' | 'system';
  idempotencyKey: string;         // gh:delivery:uuid / im:feishu:msg_id / chat:cs_x:seq
  threads: string[];              // Source 的翻译规则产出，可能多个
  actor: { kind: 'human' | 'agent' | 'bot' | 'system'; id: string; name?: string };
  addressing: 'direct' | 'mention' | 'ambient';   // 决定强度
  content: { summary: string; body: string; refs?: string[]; attachments?: string[] };
  receivedAt: number;
  disposition?: ThreadDisposition;   // 唯一的审计事实
}

/** 路由决定的唯一载体：「把批处理提到前台」要产出、也只需产出的东西 */
export type RouteDecision =
  | { action: 'accept';   threadId: string; newThread?: boolean; ticketId?: string; reason: string }
  | { action: 'attach';   threadId: string; ticketId: string; reason: string }
  | { action: 'dispatch'; threadId: string; agentId: string; sessionId: string; reason: string }
  | { action: 'stop';     threadId: string; ticketId: string; reason: string }
  | { action: 'ignore';   threadId: string; reason: string; wouldAccept?: boolean }
  | { action: 'defer';    threadId: string; until: number | { wakeOn: WakeCondition }; reason: string };

/** 责任域：agent 能被指派「负责」的资源。仓库只是其中一种 */
export interface ResourceBinding {
  id: string;                                  // rbd_*
  holder: { kind: 'agent' | 'team'; id: string };
  /** 命名空间 + 本地 id；前缀必须是已注册适配器（运行期校验，编译期不耦合） */
  resource: string;                            // 'gh:owner/repo' | 'xhs:brand_01' | 'rss:competitor-a'
  /** 一条按「可撤回性」排序的 4 级轴，不按域分词汇表 */
  scope: 'read' | 'draft' | 'publish' | 'admin';
  /** 自主档位，与 scope 正交：scope 是「允许到哪」，autonomy 是「不问就做还是先报」 */
  autonomy: 'off' | 'observe' | 'auto' | 'trusted';
  since: number;
  grantedBy: { kind: 'human' | 'agent'; id: string };
}
```

四个要点：

1. **`Thread` 是唯一持有「串行 + 订阅 + 归属」的对象**。所有锁键都变成 `thread.id`，`sessionLockKey()` 这类补丁可以删除。
2. **`Trigger` 不可变、有幂等键**。同一事件重投只产生一个处置（覆盖 webhook 重投）——这是把 mailbox 的幂等从「item 行」上移到「事件」。
3. **`RouteDecision` 是唯一审计事实**。**这就是「提到前台」的真正含义**：不是把批处理搬到 UI 上，而是把批处理的结果落成一个可以被人读的、带 reason 的对象。
4. **`ThreadStage` 是纯函数**：`deriveStage(thread, facts)`，第一个命中胜出。零写者、零竞态。

### 7.3.1 Thread 的唯一写者（**补一个设计缺口**）

> 2026-11-02 事后补记。本节原本**不存在**，而漏掉它的后果是：实现文档 §7 的 8 个阶段全部「完成」、108 个用例全绿，真实库里 `threads` 表 **0 行**。

#### 缺口是什么

原设计定义了 `Thread` 这个对象，也定义了谁读它（Inbox / Thread 视图 / 路由台），但**从未指定谁写它**。核对结果：

- 本文与实现文档全文 `grep "ensure("` → **零命中**
- 实现文档 §7.3 标题叫「主链路接线」，实际接的是 `mailbox.entityKeysOf()` 锁键、`sessionLockKey` 降级、`consolidateGroup` 去改写、决定落库——**没有一处写 `threads`**
- 唯一显式调用 `ensure()` 的是外部事件入口（webhook），而它要求先人工登记来源，实测生产 **0 条**

结果：对象建好了、接口通了、UI 画了，**没有任何真实数据走过这条路**。

这不是实现偷懒，是**任务分解里根本没有这一项**——不管谁来执行、执行得多认真，照原计划做完都是 0 行。

#### 修正：唯一写入入口

```
ThreadService.ensure(trigger) → threadId
```

`threads` 表**只允许**被这一个方法写入。任何地方不得直接 `INSERT INTO threads`——包括 repo 之外的 service、handler、脚本。

#### 三个日常调用点（各一处，且必须是该链路的唯一落库点）

| 链路 | 调用点 | 为什么是它 |
|---|---|---|
| chat | `persistChatTurn()` | stream 与 non-stream 两条路径的唯一落库点，一处覆盖两条 |
| task | `TaskService.createTask()` + 状态变更处 | 任务生命周期只有这一个写者 |
| a2a | A2A 消息发送的唯一出口 | 同一条消息不得产生两条流 |

#### 明确「谁不写」（防止长出第二个写者）

- **读路径不得触发写**：Inbox / Thread 视图 / 路由台不得在渲染时 `ensure`。派生视图写库 = 竞态 + 幂等必然失效。
- **UI 不得调用**：流由业务行为产生，不由「有人打开了页面」产生。
- **不做历史批量回填**：懒创建，首次触达才建。存量用户升级时不得扫全表（会卡启动）。

#### 不变式

1. 一个 Trigger 恰好 `ensure()` 一次（`ref` 上的唯一约束兜底）
2. `ensure()` 幂等：同 `ref` 重复调用返回同一 `threadId`，不新增行
3. 写入失败**不得**导致业务失败（流是派生视图），但**必须**留 `warn` 日志——否则「流没建」会成为查不到的盲区

#### 由此得出的验收判据（新增，之前缺失）

> **不配任何外部来源、只跑日常任务，概览能不能正确回答「谁卡在谁那儿」？**

这一问如果当初存在，第一天就会暴露主干未接。而当时的问法是「8 个阶段做完了吗」——答案永远是「做完了」。**前者问功能，后者问清单。**

### 7.4 `scope` 只有一条轴：这个动作有多难撤回

判据是两条乘积：**可见性（别人能不能看到）× 可撤回性（撤回来有多难）**。这两条在所有域上都成立：

| 级别 | 定义 | 仓库 | 社交账号 | 数据集 | 工单队列 |
|---|---|---|---|---|---|
| L0 `read` | 无副作用 | 读代码 | 看评论 | 读 | 看单 |
| L1 `draft` | 只在 agent 自己的沙箱里可见，随手可撤 | 本地分支 | 草稿箱 | 临时表 | 认领 |
| L2 `publish` | 对外可见/生效，但**可撤回** | 提 PR / 评论 | 发布 / 回评论 | append | 关单 |
| L3 `admin` | **不可撤回**，或改的是规则本身 | 合 main / 改保护分支 | 改账号设置 / 发私信 | 覆盖 / 删数据 | 改队列规则 |

每个域的原生叫法（`commit` / `publish` / `claim` / `append`）只是**显示标签**——一张纯数据映射表，零行为、零校验分支。

三条约束：
- `UNIQUE(holder.kind, holder.id, resource)` —— 一个 holder 对同一资源只有一条有效绑定；
- **同一资源同一时刻只能有一个 L3 责任人**，其余只能是低档——否则就是两个写者同时改一个东西（这个 bug 我们在 task-service 里已经付过代价）；
- **`autonomy` 与 `scope` 必须正交**：把「能发」和「不问就发」合成一档，就再也无法表达「它有权发，但每次发之前要问我」。

### 7.5 「Router」放在哪：一个角色，不是一个进程

结论：**不新增 router 进程/agent 实例，但 Router 这个能力必须有。** 理由是工程性的：router 一旦有独立 LLM 上下文就会漂移（super-agent 自己也要靠 prompt 反复约束它「不要做实现」），而漂移的代价在 Markus 上更高——一次错判会变成一张错卡、一次错审批，链条更长。

正确做法：**Router 是 Agent 的一个「场景」（scenario），不是新实体。**

```ts
type AgentScenario = ... | 'router';
routerTools = ['route_decide', 'thread_read', 'thread_attach', 'thread_ignore', 'rest'];
```

三条性质：**不新增实体**（router 会话就是该 agent 的一个记忆会话，可压缩可回忆）；**可降级**（没有 LLM 时先跑确定性规则）；**可审计**（每个回合产出 `RouteDecision[]` 落库）。

**确定性优先，LLM 兜底**：
```
第 1 层 Gate（零 LLM）：
  - 幂等命中 → 丢弃
  - addressing ∈ {direct, mention} 且 actor.kind === 'human' → 直接 dispatch（人已指定）
  - 命中已订阅 thread → 直通（不产生 Decision）
  - 明确指向既有实体（带 tsk_/req_/cs_ id 或资源键）→ attach
第 2 层 Assessment（LLM，仅当第 1 层判不了）：
  - 这条属于哪条流 / 要不要新开工作 / 是否忽略
```

两个必须写死的细节（实测踩出来的）：
- **`mention` 必须算 explicit**：只认 `direct` 会把 GitHub/IM 上每条 `@bot` 都判成「需要研判」；
- **解析点必须读两个历史落点**（`payload.extra.sessionId` 与 `metadata.sessionId`）：只读一处会静默退化成 agent 全局串行——表现是「全部串行、变慢」，**测试不会报错**。

### 7.6 直通规则（必须同时满足三条，缺一不可）

照抄 super-agent 会漏掉它的安全侧。Markus 的直通要加三条：

1. **绕过路由，但不绕过授权**：直通只改变「谁先读到」，不改变「能做什么」。权限仍由 requirement/task/review 链约束（这点 Markus 比 super-agent 强，不能因为直通而削弱）。
2. **人永远优先**：直通消息插到 worker 会话的**下一个安全点**（现有 `AttentionController` 的 preempt/defer 已能表达），而不是排到队尾。
3. **仍可被「人喊停」打断**，且**执行体无权自行宣布「用户让我停」**——停必须由路由层记录。这条是从他们 `docs/002-authorization.md` 直接抄的，很精到。

### 7.7 主动 loop：`rest` 工具 + router 承担等待

- **对 worker 用 = 危险**。N 个 worker 永不停止 = N 份常驻上下文 + N 份持续 token（心跳风暴的结构性版本）。反对。
- **对 router 用 = 正确，且优于心跳**。只有一个节点等待，且等待有条件、可中断、可审计。

```ts
rest({
  wakeOn: Array<
    | { kind: 'trigger'; filter: { threadRef?: ThreadRef } }
    | { kind: 'stage'; threadRef: ThreadRef; stage: ThreadStage }
    | { kind: 'timeout'; ms: number }          // 兜底，不用于轮询
    | { kind: 'dependency'; taskId: string }
  >,
  note?: string,
})
```

平台语义：调用后**该会话不结束、不释放上下文，但不占用 LLM**（会话挂起 ≠ 会话在跑）；任一条件命中 → 投递 Trigger 唤醒同一会话；**必须有界**（单次上限、连续次数上限、超限升级给人）；**必须可被外部打断**。

| | 心跳（现在） | rest（建议） |
|---|---|---|
| 触发 | 定时（固定节拍） | 条件（事件/阶段/超时） |
| 无事时 | 醒一次，跑指纹，可能还跑 LLM | 完全静默，零成本 |
| 上下文 | 每次心跳是新回合 | 同一会话延续，连续性天然 |

**这条同时回答了「router session 不停止、持续思考」**：它不是「不停地想」，而是「**一直在线，只在有条件时被唤醒**」。持续思考是错觉，持续**在线**才是需求。

### 7.8 自主档位：四档，绑定级生效

| 档位 | 收到外部事件时 | 能做 | 绝对不能做 |
|---|---|---|---|
| `off` | 只记录，不投递 | 无 | 任何动作 |
| `observe` | 记录 `would-accept` 并展示 | 读资源、提建议 | 建卡、改内容、发消息 |
| `auto` | gate 通过即执行 | 建卡、开草稿、提 PR、跑测试 | 合 main、发版、删数据、改他人绑定 |
| `trusted` | 直通执行 | 同上 + 可自行合并到**非保护分支** | 合 main、发版、改组织配置、动别人的卡 |

两条硬约束：**默认 `observe`**，升档必须人批一次并记 audit；**「合并 main / 发版 / 删数据」在任何档位都不可自主**——这是平台红线，不是档位参数。

### 7.9 奥卡姆审查：哪些必须硬编码，哪些是加出来的

初版我写了 7 个枚举 / 约 36 个字面量（`DomainKind` 7 值、6 套 `scope` 词汇、`ThreadKind`、`EventSourceKind` 11 值、`TriggerKind` 8 值…）。逐项过一遍后删掉 5 个：

| 原设计 | 性质 | 处理 |
|---|---|---|
| `DomainKind` 7 值 | **加出来的**。运行期真需要的只有「键唯一」和「用哪个适配器」 | 删枚举 → 命名空间键 + 前缀注册表 |
| `scope` 6 套按域词汇（22 个字面量） | **加出来的**，且会腐烂（每来一个平台就想加一个词） | 删掉 → **一条按可撤回性排序的 4 级轴** |
| `ThreadKind` 枚举 | **加出来的**。流本来就该是「关于哪个实体」 | 删枚举 → `ref` 直接用实体 id |
| `EventSourceKind` 11 值 | **加出来的**。它是适配器清单，不是类型 | 删枚举 → 注册表（`prefix: string`） |
| `TriggerKind` 8 值 | **半真**。真正决定处理的是 `actor.kind` + `addressing` + `ref` 前缀 | 降级为审计标签，不参与派发 |
| `normalize()` per source | **本质复杂度**。每个厂商 payload 不同 | **必须保留**——super-agent 也这么做 |
| 幂等键 per source | **本质复杂度**。每个厂商自己的投递 id | **必须保留** |
| `ThreadStage` 7 值 | **必须保留**。产品注意力模型的契约 | 保留 |
| `autonomy` 4 档 | **必须保留**。「谁做决定」的唯一维度 | 保留 |

**判据：硬编码只有两种合法身份** ——
1. **编译器或数据库能替你守的**（闭集 + 唯一约束 + 单一派生函数）；
2. **产品语义本身**（注意力模型、授权档位）。

除此之外都该是**注册表或数据**。**每新增一个 `if/switch` 在判断某个平台名/域名，就是一次设计错误。**

| | 初版 | 现在 |
|---|---|---|
| 核心枚举 | 7 个 | **2 个**（`ThreadStage`、`Autonomy`） |
| 枚举字面量 | ~36 | **11** |
| 加一个新平台 | 改 4 处枚举 + 3 处校验 | **注册 1 个适配器** |

**super-agent 在这里比我对的地方**：他们的 `Mandate` 把 scope / strength / 命中的规则记成**数据**，由规则判定，而不是为每种域定义一套枚举。

## 8. 明确不该抄的部分

| 不抄 | 原因 |
|---|---|
| **把 Agent Loop 搬到云端** | 他们自己在 8.4 承认：云 Loop 被攻破 → 连接的所有端侧设备都可能被控；凭据进上下文即泄露。Markus 本地优先是**卖点**，不是缺陷。要解决「离线即停」，用已有远程访问（用户自有隧道 + Hub 鉴权入口）即可——**要「可达」，不要「搬脑」** |
| **Session-per-event（每个事件一个会话）** | 他们 Ticket 与 Session 解耦是为了「一个仓库一个 agent」的单一场景。Markus 有组织图与长期记忆，会话爆炸会让 `knowledge.md` 与记忆检索迅速劣化 |
| **Router 做实现判断** | 他们的 `dispatch.md` 反复自我约束「不要展开需求、不要设计方案、不要写 checklist」——说明**靠 prompt 约束 router 不越界是脆弱的**。Markus 应该用**工具集**约束（router 根本没有编辑工具），而不是用提示词祈祷 |
| **Router 水平切分** | 他们的数据表明单 Router + 批处理在 40 trigger/min 下够用（单决定分摊 1.6s）。Markus 的规模远未到此 |
| **单层授权** | 他们的 Mandate 只管「谁能发起」。Markus 的 requirement→task→review 双层授权更强，**不要为了对齐而简化** |

**一条我们已有、他们承认缺的**（应写进对外材料）：
> 8.3 节明说「安全可靠的 A2A 仍是待探索」，而我们已经有 `agent_send_message` / `agent_ask_agent` / 群聊 / 并发分身 / 跨团队协调在真实业务里跑。我们的不足是「缺治理与节流」，不是「缺能力」。

## 9. 一句话回答老板的每个问题

| 问题 | 回答 |
|---|---|
| mailbox 之前的批量处理是不是就是 router？ | 是**雏形**，但只做排序不做决策。提到前台的是「决策」，不是「批处理」 |
| 要不要把它提到前台？ | **要**，落点是「路由决定」这个可审计对象 + 路由台 UI，不是把批处理过程可视化 |
| 同 task / 同 session 线性处理是不是 threads？ | **是同一件事**。现在是「锁」，要升级为「流」：锁只给互斥，流还给顺序、订阅、归并、阶段 |
| 要不要用 thread / router 做类型化？ | 三条**轴**（不是三个枚举）：来源注册表 × 实体命名空间 × `Stage` 闭集 |
| webhook / 订阅事件怎么做？ | 领域层 `Source`（复用 comms 做传输）+ admission + 幂等 + 订阅直通 + 「已结束的卡不被 bot 唤醒」 |
| 主动 loop 可行吗？ | **对 router 可行且优于心跳；对 worker 不可行**（成本 × N）。`rest(wakeOn)` 必须有界、可打断、有心跳保活兜底 |
| 整体该优化哪里？ | 先立对象（Thread/Trigger/Decision/ResourceBinding），再立节点（Router，observe 先上），最后立入口（Inbox）。顺序颠倒必然返工 |
| Markus 跟 super-agent 什么关系？ | **超集**。L0 单 agent 自主性（接管资源、自配置、自判断、有条件等待）必须 ≥ 它；L1 协作治理是叠加项，**不是弥补 L0 的东西** |
| 什么叫 super-organization？ | `super agent × super 协作机制`。乘法：单 agent 弱就乘出 0，协作机制坑就变成 <1。唯一度量是**单位人类注意力产出** |
| 这些枚举是不是 hardcode 太多？ | **是，删了 5 个**。只留①编译器/数据库能守的闭集 ②产品语义本身，其余改注册表 |
| agent 不都是写代码的，怎么办？ | 资源键不只仓库：`gh:o/r`、`xhs:brand_01`、`rss:competitor-a`、`kb:team-docs`；权限只有一条 4 级轴；事件来源非代码优先，`github` 只是其中一种 |

## 10. 验收判据（全文汇总 · 分层）

> 这一节是事后补的。原文档把判据散在各处（§1、§3.2、R6、R7），结果执行时**一条都没被当成门禁**——我用「测试绿了」冒充完成两次。汇总成一节，是为了让「达没达标」不再需要翻全文。

| 层 | 判据 | 怎么判（机器可执行） |
|---|---|---|
| L1 对象 | Thread / Trigger / Decision 是唯一载体 | 类型存在 + `deriveStage` 是纯函数（无 IO、无随机） |
| L2 主干 | **日常三条链路（chat / task / a2a）各写一条 Thread** | 跑一次真实对话 + 一次真实任务 + 一次真实 A2A，`threads` 表出现对应 `ref` 的行。**做不到就不算完成** |
| L3 优先 | 加了协作机制后，单 agent 端到端延迟**不上升** | 改动前后各抽样 20 条同类工作，比 P50/P95 |
| L4 注意力 | 人的待办数**不随 agent 数同步上升** | 统计「需要人介入次数 / 完成工作数」，比改动前后 |
| L5 自主 | 给一个内容 agent 一个陌生资源，**一次对话内**自己走完「声明负责 → 收第一条真信号 → 提出下一步」，全程无人点 UI | 端到端演练，录 `threads` / `dispositions` / `thread_events` 三张表的痕迹 |
| L6 安全 | `autonomy=observe` 时真实不可逆动作（发布/删除/支付）**被拦下并留 disposition** | 真实调用一次 publish，断言被拒 + 有审计行 |

**关键区分**：L1 是「东西建了没有」，L2–L6 是「目标达成了没有」。前者全绿而后者全红，是这套改造首版的真实状态——**这是把清单当功能的代价**。
