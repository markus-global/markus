## A. 严重：会让实现走偏的

### A1. 「发生了什么」有**三条并行记录**（R1 的温床）

| 记录 | 位置 | 性质 |
|---|---|---|
| `mailbox_items` | 邮箱 | **可变**：queued→processing→completed/dropped |
| `triggers` | 幂等表 | **不可变**事件 + `thread_refs[]` + `idempotency_key` |
| `thread_events` | 时间线 | **只追加**：给「来龙去脉」读 |

设计说 **Trigger ≡ MailboxItem**（同一东西），那 `thread_events` 是什么？
→ 现状是：**同一件事在三个地方各记一次**，谁是权威没写明。
**风险**：三条各自演化，时间线/审计/队列各说一套。这正是我反复修的 R1。
**已定**：见 §8 —— `triggers` 唯一事实源，`mailbox_items` 执行态，`thread_events` **删除**、时间线改派生。

### A2. `Decision` 这个词指**两件不同的事**（✅ 已解决，b4e7dfd6）

| 名字（现状） | 取值 | 回答 |
|---|---|---|
| `Disposition`（原 `RouteDecision`） | accept / attach / dispatch / stop / ignore / defer | 「这条信号该进哪条流」 |
| `AttentionAction`（原 `DecisionType`） | pick / continue / preempt / cancel / defer / merge / delegate / drop / complete / triage | 「下一轮先处理哪条」 |

设计主对账表明确：前者是**要补的**，后者是**「接下来处理哪条」**。同名不同物。
**风险**：讨论"决策"时双方说的不是一件事；代码里两个 `Decision*` 类型并存。
**已定**：两个名字各指一件事，不新增同义词层（为何否掉 `RouteVerdict` / `MailboxPickKind`）写在
`docs/architecture/concept-naming.md` §1。

### A3. 三种「状态」被混用

| 概念 | 回答 | 例子 |
|---|---|---|
| `deriveStage` | 在等谁（派生，不落库） | 等你批准 / 空闲 |
| `TaskStatus` | 治理状态（落库） | pending / review / completed |
| attention state | agent 循环此刻在干什么 | idle / deciding / working |

「运行与注意力」tab 里三者同屏出现。**风险**：用户看到两个"空闲"以为是一回事（我踩过：进程停止 vs 注意力 idle）。

### A4. 两种「授权」被混为一路

| 概念 | 回答 |
|---|---|
| Mandate（需求/任务双层审批） | **这件事能不能做**（治理） |
| ResourceBinding（scope + autonomy） | **在这块地上我能自主到什么程度**（责任域） |

两者都与"允许"有关，但一个是**逐件事**、一个是**逐资源**。
**风险**：把 autonomy 当审批用，或反之。

## B. 中等：会影响沟通与判据

### B1. `Eval` = gate + assessment，我只做了一半
gate（零 LLM 分流）有；assessment（LLM 研判）无。所以 `matchedRule` 全仓 0 处。
**风险**：说「Eval 做了」时含义不明。

### B2. `Source` = 领域概念，不是适配器
设计：Source 持**读取位点**、定义什么算事件、进领域前**丢弃机器人自己的消息**。
现状只有适配器 + `event_sources` 表。**风险**：以为"能收 webhook"就等于 Source 做完了。

### B3. 同一事实三种记号：`would accept` / `wouldAccept` / `record-only`（✅ 已解决，b4e7dfd6）
设计原文用 "would accept"；字段是 `wouldAccept`；闸门结局叫 `record-only`。
**风险**：同一个语义在文档、DB、代码里三个名字，讨论时容易漏掉一处（我确实漏过：判据写反）。
**已定**：DB 列 `would_accept`（三态 1/0/NULL）+ TS 字段 `wouldAccept` 是**同一个事实的两种拼写**，
转换只允许在 `WouldAccept`（`packages/storage/src/thread-store.ts:135`）一处；`record-only` 是
**另一个事实**（投递结局），关系写进 `docs/architecture/concept-naming.md` §2。

### B4. `Thread` = 对象还是视角？
存储上 `UNIQUE(ref)` → 一个实体一条 thread，它**是**对象。
但「来龙去脉」是**看这件事的视角**。我把它做成了一个全局目录页 = 把视角当对象。
**风险**：再有人按"目录"理解它，就会再造一个导航项。

## 8. A1 的决定：两层存储 + 一层派生（`thread_events` 直接删除）

### 8.1 Owner 的追问把设计问穿了

我原方案是「给 `thread_events` 加 `trigger_id`，降为引用，保留旧列做双读过渡」。
Owner 只问了一句：**main 分支里没有 `thread_events` 这个表吧？**

证据（本仓实测）：

| 检查 | 结果 |
|---|---|
| `main` 分支 `sqlite-storage.ts` 中 `thread_events` | **0 处** |
| 本分支 `packages/storage` + `packages/web-ui` 引用 | 22 处（读模型 + 时间线页） |

**结论：这张表从未发布过。** 于是「旧版本用户数据兼容」整节都是**为不存在的用户写的**——
我差点为一张没人有的表设计迁移方案、双读回落、可回滚列。这是典型的「给补丁写补丁」。

### 8.2 第一性原理：读模型不该是一张表

三条记录回答的不是同一个问题：

| 层 | 记录 | 回答 | 该不该落库 |
|---|---|---|---|
| **事实** | `triggers` | 这件事**发生过**（幂等键 + `thread_refs` + 不可变） | ✅ 唯一权威 |
| **执行态** | `mailbox_items` | 它被投给谁、处理到哪一步 | ✅ 可变状态，必须存 |
| **读模型** | ~~`thread_events`~~ | 给人看的来龙去脉 | ❌ **不存** |

读模型存的 `summary`/`payload` 与 `triggers.summary`/`body` 是**同一内容的两份拷贝**——
这就是 A1 的病根：两个写者，迟早不一致。而「时间线」本来只是一条查询。

**判据：一个只读视图如果被物化成表，它就必须有人负责保持同步；没人负责，它就是第二写者。**

### 8.3 决定

1. **`triggers` = 唯一事实源**：任何「发生过的事」——外部 webhook、会话消息、任务评论、A2A——都登记为一行 trigger。
2. **`mailbox_items` = 执行态**：只记投递与处理进度，不承载事件内容。
3. **`thread_events` 表删除**：时间线改为对 `triggers` 的派生查询：

```sql
SELECT t.* FROM triggers t, json_each(t.thread_refs) j
WHERE j.value = ?            -- 业务 ref（tsk_ / cs_ / a2a_ / req_）
ORDER BY t.received_at DESC, t.id DESC
LIMIT ?
```

4. **判据**：凡「发生了什么」，全仓只有 `SqliteTriggerRepo.insertOrGet` 一个写入点。

### 8.4 删除为什么是零风险的（但不是零成本）

| 风险面 | 判断 |
|---|---|
| 旧用户数据 | **无**：`main` 没有这张表，`CREATE TABLE IF NOT EXISTS` 从未在任何已发布版本执行过 |
| 代码兼容 | 无对外契约变化：`/api/threads/:ref/events` 响应形状不变（`{events:[{id,kind,actor,summary,createdAt}]}`） |
| 回滚 | 单次 revert 即可，无 schema 残留 |
| **真实成本** | 查询从「按 `thread_id` 走索引」变成「扫 `triggers` + `json_each`」。本地库量级小（单机万行内）可接受；**若 trigger 上到十万级再优化——有了真实数据再优化，不是现在猜** |

### 8.5 执行顺序（有前置条件，不能先删）

`triggers` 目前只被 `event-routes`（外部 webhook 入口）写入；而 chat / comment / a2a 的内容
只写在 `thread_events` 里。**先删表 = 时间线当场空掉。** 所以三步：

| 步 | 动作 | 回退方式 |
|---|---|---|
| **①** | 内部事件（chat / comment / a2a）改写入 `triggers` | 退回旧函数即可，两表并存不冲突 |
| **②** | 时间线读取改走派生查询 | 读取端切回旧 repo |
| **③** | 删 `thread_events` DDL / repo / 接线 / 测试 | revert |

三步各自可独立回退；①② 期间不产生第二写者（新代码只写 triggers）。

### 8.6 曾经的三个「残余」——已全部结清（含实测数据）

上一版这里写的是三条「残余」。Owner 追问「为什么老是留残余」后逐条回查，结论是：
**三条里两条根本不是残余，是我没查就写下的托词。**

| 原写法 | 真相 | 处理 |
|---|---|---|
| 「`thread_refs` 无索引，量级大要加，先不猜」 | 该测的没测 | **实测**（下表），并依据数据加了索引 |
| 「同毫秒顺序用 id 兜底，确定性但不表达真实先后」 | 有现成解没去找 | 改 `rowid DESC` = SQLite 插入序列，**就是真实先后** |
| 「A2A 摘要只能到『A → B 发了一条消息』，投递回调拿不到正文」 | **错的**：调用点上一行就有 `message` 变量 | 正文一路传下来，JSON 信封则提取可读字段 |
| （未列出）chat 只记了用户那句 | 助手回复**从未进时间线**，是缺功能不是残余 | 已补；幂等键 = message id，重连重存不会长出第二条 |

**索引实测（本机，20 次取中位数，真实建库 SQL）**

| triggers 行数 | 无索引 | 加 `idx_trg_received` |
|---|---|---|
| 1 000 | 0.18 ms | — |
| 10 000 | 1.25 ms | — |
| 100 000 | **14.71 ms**（踩在一帧 16ms 边上） | **0.24 ms** |

查询计划对照：无索引时 `USE TEMP B-TREE FOR ORDER BY`；加索引后走索引顺序，排序成本消失。
**一条索引买 60 倍**——所以它进了 schema，不是留在「以后再说」。

**现在真正的边界（不再含糊）**：JSON 数组本身索引不了，索引解决的是排序成本；
若某天单条流的 trigger 数本身到十万级，需要的是按 ref 反查的关联表，而不是更多索引。**有证据再动。**
