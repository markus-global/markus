## 0.4 为什么首版会把「UI 未完成」当成完成（判据降级）

这是本次最该记住的一条，比任何代码缺陷都贵。

| 来源 | 「完成」的判据 |
|---|---|
| 目标文档 §1 推论 2 | 加了协作机制后，单个 agent 完成一件事的**端到端延迟不得上升** |
| 目标文档 §1 推论 3 | **单位人类注意力产出** |
| 目标文档 R6 | 任一「需要人」的对象，在 Inbox **恰好出现一次** |
| 目标文档 R7 | 给 agent 一个没接过的资源，能在**一次对话内**接住第一条真实信号 |
| 实现文档阶段表（首版） | 8 个阶段 ✅、单测绿、`tsc` 通过 |

**四层降级，逐层放大**：

1. **判据降级**：产品级判据（人的注意力、端到端延迟）→ 代码级判据（模块存在、单测绿）。一旦降级，「模块都写了」就等于「做完了」。
2. **假设免验**：H1「日常主链路会创建 thread」是整套 Inbox 的地基，**从未验证**就往上建。等发现真库 `threads` 表 0 行，上层全是空壳。
3. **完成自评**：阶段表的 ✅ 是实现者自己盖的，没有独立环节拿目标判据去否决它。
4. **词汇混淆**：「代码可 review」和「功能可上线」被当成一句话说。

**最致命的一条**：所有验证都绕过了价值所在的地方。webhook 路径好测（自己 curl 一下就有输入），日常主链路难测（要真跑一天任务、需求、评论、会话）。于是测了好测的，绕过了有价值的——**路灯下找钥匙**。

**缺失的那一条判据**只有一句：*一个不配任何外部来源的用户，今天打开概览，能不能看到自己真实的待办？* 这条一加，H1 当场暴露，也就走不到「8 阶段全绿但表 0 行」。

**流程上真正该改的三条**：
1. 每条判据必须配**一条端到端可证伪验收**，且必须走**存量用户主链路**，不能写成「模块 X 完成」。
2. **地基假设先验后建**：任何「上游会为它写数据」的假设，必须先用真实数据证明有生产者。
3. **完成不能自评**：阶段表只能写「已实现」，"完成"由独立的一轮回归签。

### 0.4.1 纪律：状态只能由验收证据改，不能由「我改完了」改（2026-11-04 追加）

上面诊断的是**判据降级**；还差最后一环没堵上：**判据合格了，谁有权改状态**。
2026-11-04 核查实测：台账 §9 已记「已完成 + 提交号」，而本节 §0.5 的 8 项端到端验收**仍全是「待验」**。
两者都是我自己写的 —— 同一个人在同一小时里既说「完成」又说「没验」，说明**状态变更没有守门人**。

**规则（可判定，不靠自觉）**

| # | 规则 | 判据（反例就是违规） |
|---|---|---|
| D1 | 状态**只能**由验收证据改 | 改状态的依据必须是下一条「证据」，不得是「代码写完了 / 单测绿了 / 我 review 过了」 |
| D2 | 「证据」= **命令 + 输出** | 一条证据必含：① 可复制执行的命令（或操作步骤）② 该命令的真实输出摘录 ③ 采集时间 ④ 证据来自**真实数据面**（真实库 / 真实流量 / 真实浏览器），夹具与推演不算 |
| D3 | 无证据 ⇒ 状态**不动** | 拿不出 D2 的证据，状态最高只能是 `进行中`（A 卡交付后即是上限），提交号列填 `—` |
| D4 | 证据失效即回退 | 后续核查发现该证据不再成立（回归红、数据面变了），状态必须改回 `进行中` —— 「曾经绿过」不是永久通行证 |
| D5 | 自评不算证据 | 实现者本人的「我点过了」不算；要么附 D2 的输出，要么由**另一轮独立复验**签字 |

**证据长什么样（示例，抄格式即可）**

````
证据 E1（2026-11-04 20:31）
$ sqlite3 ~/.markus/data.db "select count(*) from threads"
14
判定：主干接线前基线为 14；卡 3 接入后应 > 14 且新增行来自 chat/task/a2a。
````

> **为什么把这条写进文档而不是只写在提交信息里**：本轮之前它只存在于我的「行为准则」里
> （`05` §四第 9 条），而准则不是校验；历史已经证明「靠自觉的规则会重演」——
> 台账脚本存在的理由正是这一句。**能变成红绿灯的规则才叫规则**，
> 剩下这两条（D1–D5）的机械化收口由卡 5 完成。

## 0.6 合并自《第一性原理复审》与《实测验收报告》的结论（原两份独立文档已并入本文）

**架构层三条结论**（原复审文档）：
1. **`UNIQUE(ref)` 不是矛盾，不该改**。一个外部对象在平台里只该有一条代理记录。真矛盾是 `threads.owner_agent`（单值且生产零写入）与 `thread_subscriptions(purpose='own')`（多值）重复表达「谁负责」——一条流只能一个 owner，才显得必须拆成多条流。**已删该三列**，多责任人由多条 own 订阅表达。

3. **`Thread` 是唯一持有「串行 + 订阅 + 归属」的对象**；`Disposition`（历史名 `RouteDecision`，2026-11-03 改名）是唯一审计事实；`deriveStage` 必须是纯函数（零写者、零竞态）。

**实测层三条发现**（原验收报告 + 本轮浏览器实测）：

```sql
  purpose   TEXT NOT NULL,                 -- 'own' | 'context'
  PRIMARY KEY (thread_id, ticket_id)
);

-- 处置：唯一审计事实
CREATE TABLE IF NOT EXISTS thread_dispositions (
  id           TEXT PRIMARY KEY,
  trigger_id   TEXT NOT NULL,
  thread_id    TEXT NOT NULL,
  action       TEXT NOT NULL,              -- accept|attach|dispatch|stop|ignore|defer
  reason       TEXT NOT NULL,              -- 必填，面板直接展示
  would_accept INTEGER DEFAULT 0,          -- observe 模式的「本该接受」
  actor        TEXT NOT NULL,              -- 'router' | 'gate' | 'human'
  created_at   INTEGER NOT NULL,
  UNIQUE(trigger_id, thread_id)            -- 幂等
);

-- 责任域绑定
CREATE TABLE IF NOT EXISTS resource_bindings (
  id          TEXT PRIMARY KEY,            -- rbd_*
  holder_kind TEXT NOT NULL,               -- 'agent' | 'team'
  holder_id   TEXT NOT NULL,
  resource    TEXT NOT NULL,               -- 'gh:owner/repo' | 'xhs:brand_01' | 'rss:competitor-a'
  scope       TEXT NOT NULL,               -- read | draft | publish | admin（有序）
  autonomy    TEXT NOT NULL DEFAULT 'observe',
  granted_by  TEXT NOT NULL,
  since       INTEGER NOT NULL,
  UNIQUE(holder_kind, holder_id, resource)
);

-- 来源配置（事件入口）
CREATE TABLE IF NOT EXISTS event_sources (
  id          TEXT PRIMARY KEY,            -- src_*
  org_id      TEXT NOT NULL,
  prefix      TEXT NOT NULL,               -- 适配器前缀：gh | xhs | rss | im-feishu
  secret      TEXT,                        -- HMAC 密钥（不落日志）
  config      TEXT DEFAULT '{}',           -- 监听范围、路由规则、observe 开关
  health      TEXT DEFAULT '{}',           -- 位点、失败率、最近错误
  created_at  INTEGER NOT NULL,
  UNIQUE(org_id, prefix, id)
);
```

### 2.2 `deriveStage()`：纯函数，不落库

```ts
export function deriveStage(f: StageFacts): ThreadStage {
  if (f.pendingApproval) return 'person:approval';
  if (f.openQuestion)    return 'person:answer';
  if (f.submittedReview) return 'person:review';
  if (f.reportedBlockedSinceHuman) return 'person:blocked';
  if (f.assignment && f.assignment.state === 'pending') return 'system:queued';
  if (!f.assignment || f.assignment.ended) return 'idle';
  return 'working';
}
```

第一个命中胜出，顺序即优先级。**这条函数是整个 UI 的排序键**，也是「卡在谁那儿」的唯一答案。

### 2.3 不变量（写成行为测试）

| # | 不变量 | 可执行的证伪方式 |
|---|---|---|
| I1 | 一个 `ref` 只有一条 thread | 并发 upsert 100 次，断言 count=1 |
| I2 | 同一 thread 同一时刻只有一个回合在跑 | 并发投 20 条同 thread 事件，断言处理序列 `startedAt` 严格不重叠 |
| I3 | 同一 `idempotencyKey` 只产生一个 disposition | 重投 50 次（含 webhook 重试），断言行数=1 |
| I4 | `disposition.reason` 永远非空 | 构造所有 action，断言 `reason.length > 0` |
| I5 | 直通不改变授权 | 构造「已订阅 thread 上的越权请求」，断言仍被审批链拒绝 |
| I6 | 人的消息不会被 router 延迟 | router 正在跑长评估时投一条 `chat/direct`，断言 P95 延迟 < 现有基线 |
| I7 | `deriveStage` 对任意事实集恰有一个值 | 属性测试，穷举 7 个布尔组合（64 种） |
| I8 | 同一资源只能有一个 L3 责任人 | 并发绑定两个 `admin`，断言第二个被拒且返回可行动提示 |
| I9 | 升级不改动旧表任何一行 | 真实旧库副本升级前后全表 dump 哈希一致（见 §6.4） |

**I6 是上线门禁**：如果新架构让人等 router，它就必须回滚——这也是「不把所有消息先送 router」的根本原因。

### 3.3 Gate 规则（第 1 层，零 LLM）

```
1. 幂等命中                                  → 丢弃（记录 duplicated）
2. addressing ∈ {direct, mention} 且 actor 是人 → dispatch（人已指定，不研判）
3. 命中已订阅 thread                          → 直通（不产生 Decision）
4. 带 tsk_/req_/cs_ id 或资源键               → attach
5. bot/CI 事件 + thread 已结束                → 只记录，不唤醒
6. 其余                                       → needs-assessment（v1 延后 + reason）
```

**两个写死的细节**（实测踩出来的）：
- `mention` 必须算 explicit——只认 `direct` 会把每条 `@bot` 都送去研判；
- 解析必须读 `payload.extra.sessionId` 与 `metadata.sessionId` 两处——只读一处会静默退化成 agent 全局串行（变慢但不报错）。

## 4. Agent 工具面

### 4.1 新增四个工具（自绑责任域）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `resource_bind` | 把自己（或本团队）绑定到某个资源，声明 `scope` 与 `autonomy` | `scope` 必须在 4 级内；同一资源 L3 只能一个负责人；升 `autonomy≥auto` 需人批 |
| `resource_release` | 解除自己的绑定 | 只能解自己的；解绑不删已有卡与产物 |
| `resource_owners` | 查某资源现在谁负责、到哪一档 | 只读，任何人可查 |
| `resource_status` | 「我负责哪些资源、各自最近发生了什么、有没有等我」 | 只读，**agent 自我感知的入口** |

### 4.2 三个设计要点

1. **升档要返回「已提交审批」而不是「已生效」**——工具结果是 agent 唯一的反馈通道，不能撒谎；
2. **绑定即订阅**：`resource_bind` 成功 → 自动建该资源 thread 的订阅，后续事件天然直通（复用现有机制，不新造）；
3. **`resource_status` 结果进 system prompt 的固定段**（尾部可变）：让 agent 每回合知道「我盯着哪几个资源、哪个有动静」——这是「主动」的真正来源，比心跳便宜且准确。

### 4.3 目标形态（内容 agent，真实场景）

```
resource_bind({ resource:'xhs:brand_01',  scope:'publish', autonomy:'observe' })
resource_bind({ resource:'rss:competitor-a', scope:'read' })
resource_status({}) →
  我负责 2 个资源：
  · xhs:brand_01   — 3 条新评论待回（scope=publish, autonomy=observe）
  · rss:competitor-a — 12 条新文章，2 条与选题相关
```

**验收判据（真实数据）**：给一个内容 agent 一个陌生的小红书账号 + 一个竞品 RSS，它能在**一次对话内**自己走完「声明负责 → 配规则 → 收第一条信号 → 提出下一步」，全程无人点 UI。

## 5. 前端

### 5.1 两条硬规则（先于任何设计）

**规则 1：任何新的通知面，必须能替代至少两个现有通知来源，否则不做。**
判据来自注意力预算：新增一个入口就消耗一份注意力，如果它只是把已有的东西再显示一次，就是净亏损。→ Inbox 上线时必须同步**降级** Work 的「待审批」红点与 Team 的「未读」聚合（让它们成为 Inbox 的入口，而不是并行的事实源）。

**规则 2：任何一个「进行中」状态，必须能被权威事实否决。**
幽灵态的结构性解法：UI 不自己推导状态，只渲染 `deriveStage()` 的结果；stage 变了 UI 就变，不存在「我以为它在跑」。

### 5.2 新增面一：Inbox（需要我）

```
┌─ 需要我 (3) ─────────────────────────────────────────┐
│ ● 验收   需求 v0.13 的 3 张卡已提交审查      [看] [批] │
│ ● 回答   小红书写手问：这周选题用 A 还是 B？  [答]      │
│ ● 阻塞   GitHub 来源：secret 验证失败 12 次   [修]      │
└──────────────────────────────────────────────────────┘
```
要点：只有 `person:approval / answer / review / blocked` 排最前；每条**自带动作按钮**；健康状态默认安静；点进去是**那条流的完整历史**（不是任务详情 + 聊天 + 通知三条线）。

### 5.3 新增面二：Thread 视图

把「会话 tab」「任务卡评论」「A2A DM」合成一条按时间排序的流：

```
┌─ thr_… GitHub #412 修复登录超时 ────── 状态: 等验收 ──┐
│ 11-02 10:12  [人]   @cto 这个登录超时能修吗          │
│ 11-02 10:13  [agent] 收到，我开一张卡                │
│ 11-02 10:20  [系统]  创建 tsk_…（已审批）             │
│ 11-02 11:04  [CI]    ✗ e2e 失败                      │
│ 11-02 11:06  [agent] 已修，PR #415 → 待评审           │
└───────────────────────────────────────────────────────┘
```
技术要点：**这不是新数据**，是 `threads` + `events` 的一层 join 视图；正文不动（不合并、不改写），只并排呈现。

### 5.4 新增面三：路由台

**「把批处理提到前台」的真正落点**：不是把批处理 UI 化，而是把**路由决定** UI 化。

```
┌─ 路由决定 ─────────────────────────────────────────────┐
│ 10:12 #412 评论  → attach  tsk_…（CI 失败属同一问题）  │
│ 10:20 @cto 提问  → dispatch cto（人指定）              │
│ 10:31 群聊闲聊   → ignore  「与任何规则无关」            │
│ 10:40 飞书群消息 → ignore  would accept ⚠ 观察模式      │
└────────────────────────────────────────────────────────┘
```
每条带 **reason**（必填，落库），可点开原文；`would accept` 是 **observe 模式**的产出——**在不做事的前提下让人看到「如果放开会自动接哪些活」**，是主动能力上线前的安全阀；用户可在这一页**撤销**一个错误 attach（`unsubscribe`）。

### 5.5 现有页面的改动（最小侵入）

| 页面 | 改动 | 理由 |
|---|---|---|
| Work | 卡片加 **stage chip**，排序默认按 stage | 一个字段解释「卡在谁那儿」 |
| Team | 会话头显示绑定的 **thread**（若有）；显示 agent 当前 stage | 消除「它在跑还是卡了」的猜测 |
| Notifications | **降级**为 Inbox 的一个过滤视图，不再独立产生未读 | 规则 1 |
| Settings | 新增「来源 / 主动模式 / 责任域」三组 | 按概念分，不按页面分 |
| AgentProfile | 显示 `autonomy` 档位 + 负责的资源清单 + 最近 20 条路由决定 | 让「它自己会动」变成可监督的 |

### 5.6 一条反直觉建议

**不要把「批处理」暴露给用户。** super-agent 从不告诉用户「我把 3 条合并成一批判断了」——用户只看到「我提的三个问题被一起回答了」。合并是**性能优化**，暴露它只是把实现细节变成认知负担。

用户该看到的只有两样：**这条流的状态**，和**为什么系统做了这个决定**。

## 6. 兼容性与迁移（存量用户）

结论：**兼容**。因为所有改动都是加法。

### 6.1 逐项对照

| 改动 | 对存量数据的影响 | 机制 / 证据 |
|---|---|---|
| 4–5 张新表 | **零**。老库启动时 `CREATE TABLE IF NOT EXISTS` 建空表，旧行一行不动 | 基线已有 43 张表 + `PRAGMA user_version`（结构版本）与 `data_migrations`（搬数据）双轨，加表是既有模式 |
| mailbox 锁键格式 | **零持久化影响**（见 6.2） | `mailbox_items` 表**没有** entityKeys 列，键是运行时从 `payload`/`metadata` 推导 |
| 合并去正文改写 | **只影响未来**。已合并的历史行保留原样，**不回溯改写** | 无迁移脚本 |
| `MailboxItemType` 15 值 | **不动**，保留降级为展示映射 | 兼容既有 UI 与历史 |
| `TaskStatus` | **不动**。`Stage` 是派生纯函数，不落库 | 零写者 |
| `threads` 回填 | **只新增行**，不改旧行 | 懒创建 + 可选批量回填，幂等可续跑 |

### 6.2 一处必须说清的事：mailbox 键变更不是数据变更

```
mailbox_items 基线列：
id / agent_id / source_type / priority / status / payload / metadata /
queued_at / started_at / completed_at / deferred_until / merged_into /
retry_count / claimed_by / lease_until / dedup_key
→ 没有 entityKeys
```

所以它是**可观测格式变更**（日志、交接文本、诊断脚本里会出现两种写法），**不是数据变更**——不需要迁移脚本。PR 描述仍要写明这一变化。

### 6.3 三个真实的兼容风险

| 风险 | 场景 | 缓解 |
|---|---|---|
| **C1 回填把旧库卡住** | 老用户数万条 task/comment，启动时一次性回填 → 启动变慢甚至超时 | **懒创建**（首次触达某实体才建 thread）+ 批量回填后台跑、可中断、可续跑；**启动路径上不做全表扫描** |
| **C2 升级瞬间的在途队列** | `queued` / `processing` 行带旧格式租约与旧键 | 基线已有 lease TTL + 僵尸清理；需验证它在新键格式下仍能正确回收冻结项 |
| **C3 回退（装了新版又退回旧版）** | 旧代码遇到未知表 | SQLite 忽略未知表；**只要不 ALTER / DROP 旧列就安全** |

### 6.4 验证方式：真实旧库副本，不用夹具

夹具会撒谎。三种场景各跑一次，全部用**真实安装的 DB 副本**：

1. **全新安装**：空目录初始化 → 与基线行为一致（新装用户与升级用户是两个不同路径，**两个都要实测**）；
2. **旧库升级**：真实旧 DB 副本 → 跑新版 → 断言：新增表存在、旧表行数与内容不变、无 `ALTER`；
3. **升级后回退**：新库 + 旧版二进制 → 断言：能启动、旧功能可用、无数据丢失。

**硬判据**：**旧表任何一行的任何字段，升级前后逐字节不变**（全表 dump 哈希对比，即不变量 I9）。

### 7.9 重排后的执行序（**取代 §7.1–7.8**）

按**依赖 + 风险**排序，不按概念分组。

| 步 | 内容 | 为什么必须在这个位置 |
|---|---|---|
| **S0** | 验收探针先立、先跑、**先红** | 唯一能判定其他项是否完成的装置。排最后 = 又回到「我自己说完成」。必须先红，否则不知道起点在哪 |
| **S1** | **设计补丁**：在 §7.3.1 指定 threads 写者（**改文档，不写代码**） | §0.9 的缺口不补，S3 会写成三份各写各的补丁 |
| **S2** | Trigger 身份 + 幂等键 | 幂等必须在**第一次写之前**。先写后补 = 历史重复行 = 需要清洗数据（已明确禁止） |
| **S3** | chat / task / a2a 三条链路 → `ensure()`；**单一写者守卫是本步伴随约束** | 三条日常流量占 99%。守卫脚本必须与这一步同次提交，不能等到后面再收 |
| **S4** | autonomy 闸门覆盖真实不可逆动作（publish / delete / pay） | 「主动 + 无闸门」是最坏组合，必须先于 S5 |
| **S5** | `rest` 工具 + 主动 loop | 有了 S4 的拦截，才有资格放开主动性 |
| **S6** | `thread_events` 表 + Thread 视图接真实事件 | 读模型。它要展示的事实必须由 S3/S4/S5 先产出，否则又是一张空表 |
| **S7** | 全量对账 + 回归 | 最终一次全跑，不留自评空间 |

#### 7.9.1 三处关键修正的理由

- **验收门禁从最后一位提到第 0 位**：判据必须由机器执行。放在最后，就能用「测试全绿」冒充完成——已发生两次（§0.4）。
- **单一写者从「阶段 5」降为「贯穿约束」**：重复副本正是在写 S3 的时候产生的。等写完再收，等于承认期间先造 4 份副本。
- **幂等从「第 4 项」提到第一次写之前**：幂等不可事后补，因为事后补需要清洗历史数据。

#### 7.9.2 每一步的通过判据（不可跳过）

| 步 | 通过条件（机器可判定） |
|---|---|
| S0 | `pnpm conformance` 能跑，且对尚未实现的项**输出红** |
| S1 | 文档里能回答「哪个函数写 threads」，且能回答「哪些地方不写」 |
| S2 | 同一 `idempotencyKey` 重投 50 次 → 只 1 行 |
| S3 | 跑一次真实对话 + 一次真实任务 + 一次真实 A2A → `threads` 出现 `cs_` / `tsk_` / `a2a_` 三类行 |
| S4 | `autonomy=observe` 时 publish 被拒 + `dispositions` 留行 |
| S5 | `rest` 在 agent 工具表可见，且等待期间无 LLM 空转 |
| S6 | 打开一条流能看到 ≥ 3 个带时间戳节点，页面顶部「诚实边界」告示被删除 |
| S7 | 全量绿 + 设计文档 §10 的 L1–L6 逐层有证据 |

## 8. 风险与失败模式

### 8.1 设计风险

| # | 风险 | 缓解 |
|---|---|---|
| 1 | **Router 挂了/卡住** → 事件积压 | 有界队列 + 超时自动走确定性 gate；积压超阈值告警给人 |
| 2 | **幂等键缺失**（某来源给不出事件 id）| 降级为「内容哈希 + 时间窗」幂等，并在 Source 健康检查里标黄 |
| 3 | **thread 归属判错**（比没归属更糟）| 直通可撤销：`unsubscribe(thread)` |
| 4 | **订阅泄漏**（一条流挂了永远不该有的执行体）| 订阅必须由某张卡持有；卡结束即回收；定期对账 |
| 5 | **责任域类型无边界膨胀** | kind 收敛为资源前缀；新平台先归入已有前缀 + 用 `key` 区分；**凑够三个真实需求才考虑新增前缀** |
| 6 | **同一资源两个 L3 责任人** → 两个写者 | 表级唯一约束 + 创建时拒绝，不靠约定 |
| 7 | **无主资源的 webhook 归属歧义** | 进「待认领」队列并在 Inbox 显示，**不得默默丢掉** |
| 8 | **agent 自称负责但拿不到 scope** | `scope` 由授权链决定，agent 不能自授 L3 |
| 9 | **自主档位默认给高了** | 默认 `observe`；升档人批一次并记 audit |
| 10 | **协作机制本身变成 <1 的因子** | 把「单兵端到端延迟不上升」写成硬验收；每新增一个需人操作的环节，必须删掉一个旧环节 |
| 11 | **把 superset 当口号而不是乘法** | 任一层最小能力集缺一项，本轮不算完成；不允许用另一层抵扣 |
| 12 | **HMAC 对重序列化后的 JSON 校验** | 只在 `readBody` 一个点保留原始字节 |

### 8.2 必须在 PR 里说明的三件事

1. mailbox 运行时键格式变化（不落库，但日志里会看到两种写法）；
2. `consolidateGroup` 不再改写正文（下游若曾依赖合并后的 `content`，需改读 `items[]`）；
3. 新增表不参与旧版逻辑（回退安全，但旧版看不到路由台数据）。
